# Functional Design 質問票 — U3 取得の作り込み（u3-fetch-robustness）

上流の成果物：`inception/units-generation/unit-of-work.md`（U3 の範囲）、`unit-of-work-story-map.md`（U3 の FR：FR4.1、FR4.2、FR4.5、FR4.7、FR4.8、FR4.10、FR4.11、NFR2〜NFR4）、`inception/requirements-analysis/requirements.md`、`inception/domain-design/components.md`（StreamPlanner・EventFetcher・EventTimeline・FetchCoordinator）。

U3 は、ストリーム名の手入力をやめ、選んだロググループの関係するストリームをすべて取得し、ストリームを跨いだ時刻順で逐次表示する。スロットリング時の再試行、ストリーム単位の部分失敗のまとめ、取得の中断（ウィンドウを閉じるときの内部処理。確認ダイアログは U7）、100 万件を表示範囲だけ描く一覧を作る。

前の作業単位から U3 に持ち越した点（U3 の範囲に含める）：

- U1 のコード生成のレビュー R-06：新しい取得を始めた時点で、前回の行と件数を消す。
- U1 の機能設計のレビュー R-08：U1 の rules.md の applies_to の名前（PageCursor・FetchOutcome）が古い。U3 で EventFetcher・FetchCoordinator を広げるときに、U3 の rules.md で正しい名前を使う。
- U2 のコード生成のレビュー R-06：絞り込みと一覧の選択のコマンドが async になり、到着順の保証が弱まった。同期のコマンドに戻すか、連番を付ける。

ここでは U3 で決める必要のある振る舞いだけを確認する。

## Q1. スロットリングや通信のエラーのとき、どう再試行しますか？

背景：FR4.5 はスロットリング時に待ってから再試行するとだけ決めています。U1 の分類では、再試行してよいエラーは Throttled（スロットリング）と Network（接続・タイムアウト）です。再試行を続けても失敗したストリームは、FR4.10 のとおり失敗として数えます。

A. Throttled と Network を、待ち時間を倍々に延ばしながら（1 秒・2 秒・4 秒・8 秒・16 秒、少しばらつきを入れる）最大 5 回まで再試行し、それでも失敗したらそのストリームを失敗にする
B. Throttled だけを、1 秒おきに最大 3 回まで再試行する。Network はすぐに失敗にする
C. 再試行は AWS SDK の標準の再試行に任せ、アプリでは追加の再試行をしない
X. Other (please specify)

[Answer]: A. Throttled と Network を、待ち時間を倍々に延ばしながら（1 秒・2 秒・4 秒・8 秒・16 秒、少しばらつきを入れる）最大 5 回まで再試行し、それでも失敗したらそのストリームを失敗にする

## Q2. ロググループのストリームを、どう列挙して取得対象を決めますか？

背景：FR4.1・FR4.2 では、DescribeLogStreams でストリームを列挙し、最初・最後のイベント時刻が時間範囲と重ならないストリーム（最後のイベント時刻は 1 時間の余裕を持たせる）を外します。Lambda などのロググループでは、古いストリームが数万から数十万あることがあり、全部を列挙すると時間がかかり、DescribeLogStreams のスロットリングにもかかりやすくなります。

A. 最後のイベント時刻の新しい順に列挙し、最後のイベント時刻が「範囲の開始 − 1 時間」より古いストリームが出てきた時点で列挙をやめる（それより後ろはすべて範囲より古いため）。最初・最後のイベント時刻を持たないストリームは、列挙の途中で見つかった分を取得対象に含める
B. ストリーム名の順にすべて列挙してから、時刻で取得対象を選ぶ（列挙は確実だが、ストリームが多いと遅い）
X. Other (please specify)

[Answer]: A. 最後のイベント時刻の新しい順に列挙し、最後のイベント時刻が「範囲の開始 − 1 時間」より古いストリームが出てきた時点で列挙をやめる（それより後ろはすべて範囲より古いため）。最初・最後のイベント時刻を持たないストリームは、列挙の途中で見つかった分を取得対象に含める

## Consolidated Summary Confirmation

回答のまとめ：

- 再試行：スロットリングと通信のエラーを、1・2・4・8・16 秒（少しばらつかせる）と倍々に待って最大 5 回まで再試行し、それでも失敗したらそのストリームを失敗にする（Q1）
- ストリームの列挙：最後のイベント時刻の新しい順に列挙し、「範囲の開始 − 1 時間」より古いストリームが出た時点でやめる。時刻を持たないストリームは、列挙の途中で見つかった分を含める（Q2）
- 同じ時刻の並び順：時刻 → ストリーム名 → 同じストリームの中では API が返した順（Q3）
- 取得中に行が途中に入るとき：画面の一番上に見えている行が動かないように位置を保つ。一番上にいるときは一番上のまま（Q4）
- 失敗の詳細：ステータス行に失敗の数を出し、押すと（キーボードでも）失敗したストリームの名前とエラーの種類・安全な詳細の一覧を出す（Q5）
- 前提：ストリーム名の手入力をなくし、ロググループ全体を取得する。ストリームは 1 つずつ順に取得する（並列化は MVP の後）。一覧は「時刻 / ストリーム名 / メッセージ」の列で、ライブラリ側が持つ行のうち表示範囲の行だけを取り寄せて描く（100 万件）。取得を止めるボタンは作らず、取得の中断はウィンドウを閉じるときの内部処理だけ（確認ダイアログは U7）
- 持ち越し分：新しい取得を始めた時点で前回の行と件数を消す（U1 の R-06）。U3 の rules.md では部品の名前を正しく使う（U1 の R-08）。絞り込みと一覧の選択のコマンドの到着順を保証する（U2 の R-06）
