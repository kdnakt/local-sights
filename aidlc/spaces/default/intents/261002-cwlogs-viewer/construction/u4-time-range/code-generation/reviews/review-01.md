### 確認した観点

- **夏時間の正しさ**：`parse_in_zone` は `LocalResult::None` を `NonexistentLocalTime`、`Ambiguous` を早い方の瞬間にしている（BR1.2）。`DateTimeInput::switch_zone` は瞬間を持ち新しいタイムゾーンで 4 桁の年に表せるときは文字列だけを作り直し、再解釈しない。そのため、遅い方の瞬間（`2024-11-03 06:30:00` UTC → New York の `01:30:00` → UTC）が往復後も保たれる（date_input と session の両方にテストあり）。持たない・表せない場合は文字列を残して解釈し直す（R-02・R-05）。`edit` は同じ文字列なら何もせず instant を保つ（BR1.5・R-06）。
- **検証の理由の順序と確認待ち**：`ValidationError::ALL` と `check_instant` は、選択 → 開始（形式／存在しない）→ 終了 → 順序の並びで、誤りがあるときは RangeOrder を出さない。取得中・確認待ちは `can_fetch` だけを false にし、新しい理由の文言を足さない（BR2.1・R-04）。空の入力は形式の誤りとして U1 と同じ扱いで、機能設計のルールと矛盾しない。
- **displayTime の合成とライブラリ側の変換**：`AppSession::display_rows` が選んだタイムゾーンで行を文字列化し、EventTimeline は変わらない（R-08）。画面側に時刻計算は残っていない（`formatUtcMillis` を削除し、`toISOString`・`Date`・`Intl` の使用なしを grep で確認）。ロックの順序（session → timeline）は `get_rows` と取得完了側（lib.rs 340〜343 行）で一致しており、デッドロックの懸念はない。
- **切替と取り寄せ直し**：`select_time_zone` は取得中・確認待ちでも通り、phase を変えず、API を呼ばない。timelineVersion が変わらないため、`useRowWindow` が `timeZone` を依存に持って取り寄せ直す。要求番号による古い答えの破棄は有効。
- **OS のタイムゾーンの代替**：読めない・空・知らない名前は UTC にして理由を返し、診断には名前だけを出す。秘密情報の禁則に触れない。確認用プログラムは UTC のまま（BR3.5）。
- **トレーサビリティと計画**：traceability.json の BR1.1〜BR3.5 と FR3.x、NFR12・13 はすべて実在するファイルを指す。計画の各手順に対応する実装があり、「計画との違い」の 8 項目は実際の diff と一致する（`fetch_check.rs` の 2 行、`build.rs` の権限、`ConnectionBar.test.tsx` など）。未実装のまま完了にされた手順は見つからなかった。
