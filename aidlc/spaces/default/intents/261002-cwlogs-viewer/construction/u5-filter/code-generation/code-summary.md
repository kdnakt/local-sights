## 主な判断

- R-02：保持ログと絞り込みの状態は LogView にまとめ、1 つの `Mutex` で守る。ページの追加と逐次の判定、破棄と結果の空化、表示範囲の取り寄せと位置の問い合わせは、すべてこのロックの中で行う。ロックの順はセッション → LogView の 2 段。filterSummary は、セッションのロックを持ったまま LogView を読んでセッションに写すため、写した値はいつも直前の状態より新しい。
- 走査は CPU だけを使うため、非同期の作業ではなく `spawn_blocking` のスレッドで行う。1 回分（4,096 行）ごとにロックを放し、`yield_now` で他のスレッドに譲る。前の走査は止める合図を持たず、filterId か timelineEpoch が変わったチケットで `Stale` になって自分で終わる（BR2.4）。
- resultVersion は FilterEngine の中で決して減らない（条件を変えても、破棄しても増え続ける）。画面は `session-changed`・`fetch-progress`・`filter-progress` が前後して届いても、版の古い絞り込みの部分を捨てる。そのため SessionView と知らせには、条件なしのときでも `filterResultVersion` を入れた（filterSummary は entities のとおり条件なしで null）。
- Filtering で走査をまだ 1 回もしていない間に届いたページは、すべて走査に任せる（scanCursor なし）。そのときも allCount は変わるため resultVersion は増やす。
- 前後の空白の除去は AppSession（変わったかどうかの判断）と FilterEngine（守りとして）の両方で行う。どちらも同じ関数で、結果は変わらない。
- 画面の FetchForm は U4 のとおりタイムゾーンの切替で作り直されるため、絞り込みの欄の文字列は App が持ち、LogFilterInput は値を受け取る形にした。作り直しても文字列も 0.3 秒待ちの状態も失われない。
- 絞り込みの欄は `type="search"`（標準部品、役割は searchbox）。Enter は取得のフォームを送らない（文字列を入れて Enter を押すと保持ログが捨てられて取り直しになるのを避けるため）。
- 秘密情報：U5 は新しく AWS を呼ばず、新しい診断ログは「走査が異常に終わった」という事実だけを出す。

## 計画との違い

1. Red は 2 つの形で記録した。`filter.rs` は `todo!()` の骨組みに対する実行時の失敗、`log_view.rs` と `timeline.rs` はまだない型・項目・関数を呼ぶコンパイルの失敗。
2. 計画の部品の表にない `timeline.rs`（U3 のモジュール）を変えた。RowWindow の新しい項目（entities.md の RowWindow）と、R-08 の「U3 の索引で timestamp を引く」ための `timestamp_of`。テストを先に書いた。
3. 走査の知らせ `filter-progress` は、計画の「走査の 1 回分ごと」ではなく、100 ミリ秒に 1 回までにまとめ、Ready のときは必ず送る。結果そのものは 1 回分ごとにロックの中で更新される（画面がその間に取り寄せれば、ここまでに見つかった行が返る）。100 万件で約 250 回分あり、毎回送ると画面の取り寄せが重なるため。
4. SessionView・FetchProgressUpdate・FilterProgressUpdate に、entities.md にない `filterResultVersion`（条件なしでも持つ版）を足し、画面は版の古い知らせの絞り込みの部分を捨てる（BR3.6 の「古い版は捨てる」を知らせにも当てた）。
5. 絞り込みの欄の文字列は FetchForm ではなく App が持つ（FetchForm はタイムゾーンの切替で作り直されるため）。FetchForm は受け取った値で LogFilterInput を置く。
6. 絞り込みの欄では Enter で取得のフォームを送らない（U1:BR6.2「どの入力欄でも Enter で取得」の例外。絞り込みは取得条件ではないため）。README の確認項目に書いた。
7. `useRowWindow` の引数を位置の並びからオブジェクトに変えた（引数が 8 つになるため）。呼び出し元は LogTable だけ。
8. 計画の画面のテストの一覧にない `FetchForm.test.tsx`（取得中も使え、確認待ちで使えない）と `LogTable.test.tsx`（結果の版では一番上の行を保ち、filterId が変われば一番上に戻る）に 1 件ずつ足した。
9. テストの件数は目安どおりか多い（filter 8・log_view 8・session 5・結合 4・画面側 13）。少なくはしていない。

## まだ確かめていないこと・未解決

- 画面での見た目と操作（0.3 秒待ちの体感、取得中の逐次、100 万件近いときの絞り込み中のスクロールと入力の反応が 1 秒以内か）は、開発者本人の手元で行う（`README.md` の「Log filter (U5)」）。速さは作業環境の Linux コンテナでの計測で、NFR1・NFR2 が求める開発者の Mac での計測ではない。
- `std::sync::Mutex` は公平ではない。走査は 1 回分ごとにロックを放して `yield_now` で譲るが、画面の取り寄せが待つ時間は最長で 1 回分（リリースで 1 ミリ秒未満の見込み）で、手元の確認で確かめる。
- 走査のスレッドが異常に終わった場合（`unwrap` を使っていないため起きない見込み）は、標準エラーに事実だけを出し、結果は Filtering のまま残る。文字列を変えれば新しい走査が始まる。自動で直す仕組みは置いていない。
- 一致の判定はメッセージごとに小文字化した文字列を作る。上の計測のとおり上限に対して十分に速いため、ASCII の速い道などは足していない。
- リポジトリにはまだ `deny.toml` と CI の設定がないため、`cargo-deny` は実行していない。U5 で新しい依存は足していない（`Cargo.lock` の変更なし）。
- 作業環境のディスクの空きが少ない（作業の終わりで約 3.1 GB）。リリースビルドの後は `target/release` を消した。
