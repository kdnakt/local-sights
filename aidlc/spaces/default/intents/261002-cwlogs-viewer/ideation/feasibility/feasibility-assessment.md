# Feasibility Assessment — CloudWatch Logs ローカルビューア

上流の成果物：`intent-statement`（`aidlc/spaces/default/intents/261002-cwlogs-viewer/ideation/intent-capture/intent-statement.md`）。質問票の回答は `feasibility-questions.md` の Q1〜Q9 を指す。

## 結論

**条件付きで実現可能（Go）。** 意図整理の課題は「古いロググループの過去ログを、マネコンで見えなくても確実に閲覧できること」（intent-statement）である。これは GetLogEvents をストリーム単位で呼ぶことで実現できる見込みが高い。ただし、対象規模（ストリーム数千以上・数百万件以上、Q6）と API のスロットリング上限があるため、ロググループ全体を毎回横断取得する方式は MVP には向かない。MVP は利用者が選んだロググループ・ストリーム（または時間範囲）だけを取得する方式に絞る（Q9）。この条件であれば、1 週間以内という期限（Q5）にも収まる見込みである（見積もりは下の仮説を参照）。

## 前提の確認（ツールが成り立つ根拠）

- 意図整理の Q9 で、利用者は「マネコン（FilterLogEvents）では見えなかった過去ログが、CLI の get-log-events では見えた」と確認済み（intent-statement）。同じ API を使うので、ツールの前提は成り立つ。
- 原因（保持期間、取り込み時刻、ロググループの再作成など）は調べない方針（Q8）。そのため「GetLogEvents なら必ず見える」ことは、この 1 件の観測以上には保証されない。これはリスクとして RAID ログ（R-01）に記録する。

## 技術的な実現性

| 観点 | 評価 | 根拠 |
|------|------|------|
| ストリーム単位の取得 | 実現可能 | GetLogEvents は logStreamName が必須で、1 回あたり最大 1 MB または 10,000 件を返す（AWS API リファレンス） |
| ページングの終端判定 | 実現可能（注意が必要） | 終端では渡したトークンと同じトークンが返る。空ページでも続きがありうる。トークンの有効期限は 24 時間（AWS API リファレンス） |
| 無限ページングの回避 | 実現可能（注意が必要） | startFromHead=true で endTime を指定しないと、書き込みが続くストリームではページングが終わらないことがある（AWS API リファレンス）。古いロググループが対象なので影響は小さいが、終了時刻を常に指定する設計が必要 |
| 取得速度（MVP の範囲指定方式） | 実現可能 | 選んだストリームだけを読むので、呼び出し回数は対象範囲の件数に比例する。例：10 万件なら最低 10 回程度の呼び出し（1 ページ 10,000 件で満杯の場合）。ページが部分的に埋まる場合は回数が増える |
| 取得速度（ロググループ全体の横断） | MVP 後に再評価 | GetLogEvents の上限はアカウント・リージョンあたり毎秒 25 回（us-west-2、eu-west-1、eu-central-1 などは毎秒 10 回）で、引き上げ不可（CloudWatch Logs クォータ）。ストリーム数千以上（Q6）を各 1 回読むだけで数分かかる |
| 複数アカウント・複数リージョン | 実現可能 | プロファイルとリージョンを切り替えて同じ API を呼ぶだけで、追加の AWS 側設定は不要（Q1） |
| 認証方式 | 実現可能（仮説） | SSO、アクセスキー、AssumeRole、環境変数をすべて使う（Q2）。AWS CLI と同じ設定ファイル・認証チェーンを読めば対応できる見込み。具体的な対応範囲は要件分析・開発ルール確認で確認する |
| 将来の Insights 風クエリ | 実現可能（範囲は未定） | 取得済みイベントに対してローカルでクエリを実行する方式なら、AWS 側の制約は取得部分だけになる。どこまで実装するかはスコープ定義で決める（intent-statement の Q10） |

## AWS 環境の観点（platform engineer の視点）

- AWS 側にリソースは作らない。読み取り API を呼ぶだけで、インフラ費用は発生しない。
- スロットリング上限はアカウント・リージョン単位で共有される。マネコンや他のツールが同じアカウントで API を使っていると、上限に早く達する。リトライと待機（バックオフ）は必須である。
- 料金はできるだけ抑えたい方針（Q7）。取得済みデータの再利用（任意のキャッシュ、Q3）は、料金と API 呼び出し回数の両方を減らす。CloudWatch Logs の API 呼び出しやデータ転送の料金は、まだ公式価格表で確認していない（RAID ログ I-01）。
- 必要な IAM 権限は読み取り系に限られる見込み（GetLogEvents、DescribeLogGroups、DescribeLogStreams など）。最小権限ポリシーの例を README で提示できる（OSS 利用者向け）。

## コンプライアンス・データ取り扱いの観点（compliance specialist の視点）

- ログに機密情報（個人情報・認証情報など）が含まれうる（Q3）。そのため、取得したログは既定ではメモリ上だけで扱い、ディスクへのキャッシュは利用者が明示的に選んだ場合のみとする（Q3）。
- OSS として公開する（intent-statement）ため、利用者ごとに扱うデータの種類は異なる。ツールは AWS 認証情報を独自に保存・送信しない。外部へのテレメトリ送信もしない。
- 特定の規制（PCI-DSS、HIPAA など）への準拠は、今回の回答では求められていない。ローカルで動く読み取り専用ツールで、データは利用者自身の環境から出ないため、規制対応の追加作業は想定しない（RAID ログ A-03）。

## 規模・期限の評価

- MVP 期限 1 週間（Q5）、Rust の経験あり（Q4）、MVP は範囲指定取得に限定（Q9）。この組み合わせなら、取得・表示・フィルタの最小構成は期限内に収まる見込み（仮説。RAID ログ A-02）。
- 意図整理の成功指標「数万〜数十万件でも実用的な時間でフィルタできる」（intent-statement）は、範囲指定取得なら対象件数がこの規模に収まるので、達成できる見込み。「実用的な時間」の数値は要件分析で決める（intent-statement の assumption）。
- ロググループ全体の横断取得（数百万件以上、Q6）は MVP 後の課題とする。並列取得、キャッシュ、差分取得などの工夫が必要になる。

## 推奨事項

1. MVP は「プロファイル・リージョン・ロググループ・ストリーム（または時間範囲）を選び、その範囲を取得して表示・フィルタする」に絞る（Q9）。
2. 取得では終了時刻を常に指定し、トークンの終端判定とスロットリング時の待機・再試行を必須要件にする。
3. ディスクへのキャッシュは任意機能とし、既定は無効にする（Q3、Q7）。
4. 料金は要件分析までに公式価格表で確認する（RAID ログ I-01）。
5. ロググループ全体の横断取得と Insights 風クエリの範囲は、スコープ定義で MVP 後の項目として整理する。
