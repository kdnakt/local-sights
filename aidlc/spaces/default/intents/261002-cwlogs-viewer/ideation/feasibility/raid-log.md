## Risks

| ID | リスク | 発生可能性 | 影響 | 対応方針 | 出典 |
|----|--------|-----------|------|----------|------|
| R-01 | 原因を調べないため、他の古いロググループでは GetLogEvents でも過去ログが見えない可能性を排除できない | 低〜中 | 高（ツールの価値の前提が崩れる） | 受容。観測できた事象（CLI では見えた）を前提に進め、見えない例が出たら原因調査を別途検討する | intent-statement（Q9）、Q8 |
| R-02 | スロットリング（毎秒 25 回、一部リージョンは 10 回）で取得が遅くなる、またはエラーになる | 高（規模が大きいため） | 中 | 軽減。待機・再試行を必須にし、MVP は範囲指定取得に絞る | CloudWatch Logs クォータ、Q6、Q9 |
| R-03 | 同じアカウントでマネコンや他のツールも API を使っていると、上限に早く達する | 中 | 中 | 軽減。再試行で吸収し、取得の進み具合を利用者に見せる | CloudWatch Logs クォータ |
| R-04 | ページングの終端判定を誤り、取りこぼしや無限ループが起きる | 中 | 高 | 軽減。終了時刻を常に指定し、トークンの終端判定をテストで確認する | AWS API リファレンス |
| R-05 | ディスクキャッシュを有効にした利用者の端末に機密情報が残る | 中 | 中 | 軽減。既定は無効にし、有効化時に保存場所と削除方法を明示する | Q3 |
| R-06 | 1 週間の期限に対して、複数アカウント・全認証方式・フィルタまで含めると作業が膨らむ | 中 | 中 | 軽減。MVP の範囲をスコープ定義で確定させる | Q1、Q2、Q5 |
| R-07 | 料金が想定より高くなる | 低〜中（価格は未確認） | 中 | 軽減。公式価格表で確認し（I-01）、取得済みデータの再利用を用意する | Q7 |

## Assumptions

| ID | 前提 | 確認方法・期限 | 出典 |
|----|------|----------------|------|
| A-01 | AWS CLI と同じ設定ファイル・認証チェーンを読めば、SSO、アクセスキー、AssumeRole、環境変数のすべてに対応できる | 開発ルール確認・要件分析で、使う SDK の対応範囲を確認する | Q2 |
| A-02 | 範囲指定取得に絞った MVP（取得・表示・フィルタ）は、Rust 経験者 1 人で 1 週間以内に作れる | スコープ定義で MVP 範囲を確定した時点で再見積もりする | Q4、Q5、Q9 |
| A-03 | 特定の規制フレームワークへの準拠は不要（ローカル実行の読み取り専用ツールで、データは利用者の環境から出ない） | 利用者から規制要件の指定があれば見直す | 本ステージの回答（規制要件の指定なし） |
| A-04 | 対象のロググループは古く、新しいイベントの書き込みはほぼない | 取得時に終了時刻を指定すれば、この前提が外れても問題は起きない | intent-statement |
| A-05 | 「実用的な時間」の数値目標は要件分析で決める | 要件分析ステージ | intent-statement（assumption） |
