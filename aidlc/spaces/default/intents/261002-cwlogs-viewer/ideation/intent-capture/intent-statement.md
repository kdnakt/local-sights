# Intent Statement — CloudWatch Logs ローカルビューア

## Problem Statement

- マネジメントコンソールの FilterLogEvents や Logs Insights では、古いロググループの過去ログが見えないケースがある。[desc]
- 実際に、Logs Insights が使えない古いロググループをマネジメントコンソール（FilterLogEvents を使用）で閲覧したところ過去ログが見えなかった。ログ削除の記録はなく、CLI の get-log-events では同じ過去ログが見えた。[Q9]
- この事象の原因（保持期間、取り込み時刻、API の仕様差など）はまだ特定していない。[Q9]
- 解決したい一番の課題は、古いロググループの過去ログを、マネコンで見えなくても確実に閲覧できることである。[Q1]
- そのために、GetLogEvents API を使ってロググループ／ログストリームのログを閲覧する、ローカルで動く Rust 製クライアントアプリを作る。[desc]

## Target Customer

- 主な利用者は開発者本人であり、あわせて OSS として公開し、不特定の利用者にも使ってもらう。[Q2]
- 利用者が得る価値は、マネコンでは見えない古いロググループの過去ログを確実に閲覧できることである。[Q1]

## Success Metrics

| 指標 | 判定方法 | Source |
|------|----------|--------|
| 古いログの表示 | マネコンで見えなかった特定の古いロググループの過去ログが、このツールで表示できる | [Q3] |
| 操作の少なさ | 指定した期間・ストリームのログを、CLI より少ない操作で表示・フィルタできる | [Q3] |
| 大量イベントでの実用性 | 数万〜数十万件規模のイベントでも、実用的な時間でフィルタ結果が返る（具体的な秒数は未確定。下の Assumptions & Open Questions を参照） | [Q3] |

## Initiative Trigger

- 実務の調査で今まさに困っており、早く使えるものが欲しい。[Q4]

## Initial Scope Signal

- workflow-selected scope：`local-tool`（このワークフローの進め方として選ばれたもの）。[scope]
- user-confirmed product boundary：ローカルで動くクライアントアプリであり、AWS へのデプロイは不要。[Q8]
- 機能の段階：まずはログ表示とフィルター、最終的には Logs Insights のような複雑なクエリも実装したい。[desc]
- MVP と将来目標（Logs Insights のような複雑なクエリ）の境界は、このステージでは確定させず、スコープ定義ステージで確認する。[Q10]

## Assumptions & Open Questions

- [assumption] 成功指標「数万〜数十万件規模のイベントでも実用的な時間でフィルタ結果が返る」の「実用的な時間」の具体的な目標値（例：何秒以内か）は、要件分析ステージで数値として確定させる前提とする。
