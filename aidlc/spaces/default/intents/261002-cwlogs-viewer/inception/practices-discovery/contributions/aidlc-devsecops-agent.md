## Contribution

### 前提と読んだもの

- リードのドラフト `team-practices.md`、`discovered-rules.md`、`evidence.md`（同じディレクトリ）を読んだ。
- 根拠として `aidlc/spaces/default/memory/org.md`、`aidlc/spaces/default/memory/project.md`、`ideation/approval-handoff/initiative-brief.md`、`ideation/feasibility/constraint-register.md` を読んだ。特に関係する制約は C-R1（ログに機密が含まれうる。既定はメモリ上だけ、ディスクキャッシュは利用者が選んだ場合のみ）、C-R2（認証情報を独自に保存・外部送信しない、テレメトリなし）、C-O4（OSS 公開。README で必要な IAM 権限を示す）、C-E2（SSO・アクセスキー・AssumeRole・環境変数）、C-T8（読み取り API のみ）。
- グリーンフィールドで、アプリのコード・CI・リンタ設定はまだない。以下はすべて**提案**であり、確定したチームの事実ではない。ハードな制約は**候補**として挙げるだけで、採否は人間がインタビューで決める。
- 想定する脅威の範囲：サーバーを持たないローカルアプリのため、主な守る対象は (1) 利用者の AWS 認証情報、(2) 取得したログ本文（機密を含みうる）、(3) OSS として配布する成果物とその依存関係（サプライチェーン）、(4) 公開リポジトリそのもの（認証情報の混入、CI の悪用）である。

### 1. リンタ・フォーマッタをセキュリティの関門として使う（Code Style への追記案）

リードの `rustfmt` / `clippy` 案に賛成し、次を追加で提案する。

- マージ前の CI で `cargo fmt --check` と `cargo clippy --all-targets --locked -- -D warnings` を実行し、失敗したらマージしない（警告をエラー扱いにするかはインタビューで確認）。
- `Cargo.toml` の `[lints]` で `unsafe_code = "forbid"` を設定する案。GUI フレームワークや AWS SDK など依存先の `unsafe` は対象外で、自分のコードだけを縛る。FFI が必要になった場合は、理由を書いた上で該当モジュールだけ許可する。
- 情報漏えいにつながりやすい書き方を `clippy` で禁止する案：`dbg_macro`、`print_stdout` / `print_stderr`（アプリのログは `tracing` 等のロガー経由に限る）、`unwrap_used` は警告程度（パニック時のメッセージに値が出るのを減らす目的。期限との兼ね合いで任意）。

### 2. SAST・DAST

- **SAST**：Rust では型システム・借用検査と `clippy` が実質的な第一層になる。MVP では上の `clippy` 設定と `unsafe_code = "forbid"` で足りると考える。追加の静的解析（GitHub CodeQL の Rust 対応、Semgrep の Rust ルール）は OSS 公開リポジトリなら無料で使える可能性が高いが、Rust 対応の成熟度は導入時に確認が必要（仮定）。MVP 後の任意項目として提案する。
- **DAST**：サーバーや公開エンドポイントがないため**対象外**とする。代わりに、ログ本文という信頼できない入力を扱う処理（時刻順マージ、部分一致フィルター、キャッシュの読み込み）の境界テストを Testing Posture の中で扱う（品質担当と重なるため、ここでは観点の指摘にとどめる）。

### 3. 認証情報・秘密情報の扱い（リポジトリ・ログ・CI）

- **リポジトリ**：GitHub の secret scanning と push protection を有効にする（公開リポジトリでは無料）。加えて、手元のコミット前に `gitleaks` 等の pre-commit フックを任意で使う案。テストのフィクスチャには実在しない値（AWS 公式ドキュメントの例示用キー `AKIAIOSFODNN7EXAMPLE` など）だけを使う。
- **アプリのログ・エラー表示**：アプリ自身のログ（ファイル・標準エラー・画面のエラー表示）に、アクセスキー、シークレットキー、セッショントークン、SSO トークンを出さない。取得したログ本文も、既定のログレベルではアプリのログに出さない。AWS SDK の認証情報型を `Debug` 出力したときに値が伏せられるかは、採用するクレートで確認が必要（未確認）。
- **認証情報の読み方**：AWS SDK の既定の認証チェーン（プロファイル、SSO、AssumeRole、環境変数）に任せ、アプリ独自に認証情報を保存・キャッシュ・送信しない（C-R2）。プロファイル設定の `credential_process` は SDK が外部コマンドを実行する仕組みで、AWS CLI と同じ挙動になることを README に明記する案。
- **CI**：MVP では CI に AWS 認証情報を置かない。AWS 呼び出しはモック／スタブでテストし、実アカウントでの確認は開発者の手元で行う。将来 CI から実 AWS を呼ぶ場合は、長期のアクセスキーではなく GitHub OIDC と読み取り専用ロールを使う。

### 4. 依存関係・サプライチェーン（Rust）

- **ロックファイル**：配布するアプリ（バイナリ）なので `Cargo.lock` をコミットし、CI とリリースビルドは `--locked` で行う。
- **脆弱性スキャン**：`cargo-deny`（RustSec 勧告、ライセンス、取得元、重複・禁止クレート）を CI で毎回実行する。`cargo-audit` だけでもよいが、OSS としてライセンス確認も一度に済む `cargo-deny` を推す。
  - 関門案：RustSec の脆弱性勧告に該当したらマージ・リリースを止める。「保守されていない」等の勧告は警告にとどめる。例外は `deny.toml` に理由と見直し期限を書いて登録する。
  - 取得元：crates.io 以外（git 直接参照など）を既定で禁止し、必要なら個別に許可する。
  - ライセンス：配布物に含めてよいライセンスの一覧を決める（自分の OSS のライセンス選定とセットでインタビューで確認）。
- **定期更新**：Dependabot を `cargo` と `github-actions` の両方に設定する。公開後に新しい勧告が出たときに気づけるよう、`main` に対する定期スキャン（週 1 回など）も CI に入れる案。
- **GitHub Actions 自体の守り**：ワークフローは `permissions: contents: read` を既定にし、必要なジョブだけ権限を足す。サードパーティの Action はコミット SHA で固定する。フォークからの PR に対して `pull_request_target` で秘密情報やビルド成果物を扱う構成は避ける。
- **配布物**（リードの Deployment 案で GitHub Releases を選んだ場合）：リリースはタグを起点に CI で作り、手元のビルドを手動アップロードしない。チェックサム（SHA-256）を添える。GitHub の artifact attestation（ビルド来歴の証明）や SBOM（`cargo-cyclonedx` 等）は MVP 後の任意項目とする案。
- **macOS の署名・公証**：署名しないバイナリを配る場合、利用者に Gatekeeper の回避を案内することになり、それ自体が安全性の低い習慣を促す。MVP では「ソースから `cargo install` / `cargo build` のみ」とするか、署名・公証まで行うかを、配布方法と一緒にインタビューで決めることを提案する。

### 5. OSS 利用者への最小権限 IAM の案内

- アプリは読み取り API だけを呼ぶ（C-T8、対象外の「ログの変更操作」）。README に最小権限ポリシーの例を載せる（C-O4）。必要なアクションは `logs:DescribeLogGroups`、`logs:DescribeLogStreams`、`logs:GetLogEvents` の 3 つを想定。
- リソースは可能な限りロググループの ARN に絞る例を示す。`DescribeLogGroups` のリソース指定の可否、KMS で暗号化されたロググループで呼び出し側に追加の権限が要るかは、要件分析までに AWS 公式ドキュメントで確認する（未確認の仮定）。
- アプリのコードでも、上の 3 つ以外の CloudWatch Logs 操作（特に書き込み・削除系、FilterLogEvents、Logs Insights）を呼ばない。レビュー観点として明記するか、ハードな制約にするかはインタビューで確認する。

### 6. 機密を含みうるログ本文とキャッシュ

- **既定はメモリ上だけ**（C-R1）。キャッシュ無効時は、取得したログ本文を一時ファイルを含めてディスクに書かない。
- **キャッシュを有効にした場合**：
  - 保存場所は利用者ごとの領域（macOS では `~/Library/Caches/<アプリ識別子>/` など）とし、ディレクトリは所有者のみ（0700）、ファイルは 0600 で作る。
  - キャッシュのキーにアカウント ID・プロファイル・リージョン・ロググループを含め、別アカウントの結果が混ざらないようにする。
  - 平文で保存するか、アプリ側で暗号化するか（macOS キーチェーンの鍵を使う等）、OS のディスク暗号化（FileVault）に任せるかは未決。期限を考えると「平文 + 権限制限 + 有効化時の注意書き + FileVault 前提を README に明記」が現実的と考えるが、インタビューで確認する。
  - 「キャッシュ削除」は対象ファイルを実際に削除する（論理削除にしない）。
- **ログ本文は信頼できない入力として扱う**：表示は標準部品のプレーンテキストに限り、HTML やリッチテキストとして解釈しない。URL の自動リンク化や、ログ本文を外部コマンド・シェルに渡す処理を作らない。極端に長い行や大量の件数で固まらないことは、テスト観点として品質担当に渡す。
- **テレメトリ・クラッシュレポート**：送信しない（C-R2）。パニック時の出力にログ本文や認証情報が含まれないよう、エラーメッセージの組み立て方をレビュー観点にする。

### 7. team.md の 5 セクションへの割り当て案

practices-discovery が書く先は 5 セクションに限られるため、上記は次のように振り分けることを提案する（リードの統合判断に委ねる）。

| セクション | 追記案 |
|------------|--------|
| Way of Working | 個人開発でも `main` へは PR 経由とし、CI（fmt / clippy / test / cargo-deny / secret scanning）の通過をマージ条件にする。`main` への force push を禁止するブランチ保護。 |
| Testing Posture | AWS 呼び出しはモック、CI に AWS 認証情報を置かない。ログ本文の境界ケース（長大な行、制御文字、空ページ）をテスト観点に含める。 |
| Deployment | リリースはタグから CI でビルドし、チェックサムを添える。署名・公証の方針。依存関係の定期スキャン。 |
| Code Style | `-D warnings`、`unsafe_code = "forbid"`、`dbg_macro` 等の禁止、アプリのログに認証情報・ログ本文を出さない。 |
| Walking Skeleton | 薄い一本を作る場合も、最初から `Cargo.lock` コミット・CI の関門・secret scanning を入れておく（後付けより安い）。 |

### 8. ハードな制約の候補（人間の確認待ち。ルールではない）

リードの確認候補 6 件に加え、次を候補として挙げる。人間が明言した場合のみ `discovered-rules.md` に `ALWAYS` / `NEVER` の形で載せる。

- 候補：NEVER AWS の認証情報（アクセスキー、シークレットキー、セッショントークン、SSO トークン）をリポジトリ、アプリのログ、画面のエラー表示、キャッシュファイルに書き込まない。
- 候補：NEVER CI（GitHub Actions）に長期の AWS アクセスキーを登録しない。
- 候補：NEVER `DescribeLogGroups` / `DescribeLogStreams` / `GetLogEvents` 以外の CloudWatch Logs API を呼ばない。
- 候補：NEVER テレメトリやクラッシュレポートを外部に送信しない。
- 候補：ALWAYS `Cargo.lock` をコミットし、CI とリリースビルドは `--locked` で行う。
- 候補：ALWAYS マージ前の CI で `cargo-deny`（または `cargo-audit`）を実行し、脆弱性勧告に該当したらマージしない（例外は理由と期限付きで登録）。
- 候補：ALWAYS ディスクキャッシュは所有者のみ読み書きできる権限で作り、キャッシュ削除では実ファイルを消す。
- 候補：NEVER ログ本文を HTML として解釈したり、外部コマンドに渡したりしない。

4. 配布方法と macOS の署名・公証（リードの論点 4 と同じ。署名なしバイナリ配布の可否を含む）。
