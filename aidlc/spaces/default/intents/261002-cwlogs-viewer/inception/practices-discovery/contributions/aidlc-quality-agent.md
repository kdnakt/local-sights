## Contribution

品質（テスト）の観点から、リード下書き `team-practices.md` の `## Testing Posture` を中心に、統合時に取り込める内容と、インタビューで決めるべき論点をまとめる。グリーンフィールドのため、以下はすべて **提案** であり、確定したチームの事実ではない。

### 2. テストの進め方（Methodology / Ordering）

- **リードの提案（`test-after`）に同意する。** 期限が約 1 週間の個人開発では、層を実装してからその層のテストを書く進め方が最も負担が少ない。
- ただし、インタビューでは次の 3 案を示すのがよい（選ばれた案は `team-practices.md` の 2 項目にそのまま書く）。
  - **A. `test-after`**（既定）：テスト可能な層ごとに、実装してからその層のテストを書いて実行する。
  - **B. `custom`**：時刻順マージ・ページ終端判定・再試行・タイムゾーン変換など **純粋なロジック層だけはテストを先に書き**、AWS 接続層と GUI 層は実装後にテストを書く。仕様が入出力で明確に書ける部分だけ先にテストを置くことで、無限ループ（ページ終端の判定漏れ）や順序の崩れを早く捕まえられる。
  - **C. `tdd`**：全層でテストを先に書く。GUI 層では実質的に成立しにくく、期限に対して重いため推奨しない。
- いずれの案でも `Methodology` と `Ordering` は明示的に書く（Code Generation はこの 2 項目だけを読んで進め方を決めるため）。

### 3. カバレッジ下限（`local-tool` が org.md の一覧にない件）

- org.md を文字どおり読むと、`local-tool` には **追加のカバレッジ下限は自動では適用されない**（`mvp` 等の 80% は適用されない）。一方で Test Strategy `Standard` によるテストの量と種類（単体＋結合）は適用される。この「下限なし」が意図どおりかは人間が決めるべき事項であり、黙って `mvp` 相当を当てはめることも、黙って下限なしにすることも避ける。
- 一度下限を書くと Build and Test はそれを下げられないため、**期限に対して現実的な値と範囲** を選ぶことが重要。選択肢の提案：
  - **A. 数値の下限なし**。代わりに「GUI に依存しない層の公開関数には必ずテストがある」ことを条件にする。
  - **B. GUI に依存しない層（ライブラリ側）に限り 80% 行カバレッジ**。GUI 層（ウィンドウ・描画）とバイナリの起動部分は計測対象から除外する。品質側の推奨はこの案。
  - **C. ワークスペース全体で 80% 行カバレッジ**。GUI の描画コードは自動テストで通しにくく、期限内に達成できないおそれが高いため推奨しない。
- 計測ツールは `cargo-llvm-cov` を提案する（macOS と Linux の両方で動き、除外指定や下限で失敗させる指定ができる）。`cargo-tarpaulin` は主に Linux 向けで、macOS 開発機で同じ数値を確認しにくい。

### 4. マージ前の品質ゲート（CI）

- org.md の「マージ前の CI 実行」はスコープ別下限に紐づいているため、`local-tool` では自動では必須にならない。OSS として公開するため、**マージ前に CI が通っていることを必須にする** ことを提案する（インタビューで確認）。
- CI の **実装** は後続の `ci-pipeline` ステージで行うが、**どのチェックが失敗したらマージを止めるか** は開発ルールとして今決めておくべき事項である。提案するゲート：
  1. `cargo fmt --all -- --check`
  2. `cargo clippy --all-targets -- -D warnings`（警告をエラー扱いにするかはインタビューで確認。リードの論点 5 と同じ）
  3. `cargo test --workspace`（任意で `cargo-nextest`）
  4. カバレッジ下限を設ける場合のみ：`cargo llvm-cov` で下限未満なら失敗
- 実行環境は GitHub Actions を想定（公開リポジトリは無料枠で macOS ランナーも使える）。対応 OS が macOS のみのため、**少なくとも macOS ランナーでのビルドとテスト** を推奨する。GUI に依存しない層のテストは Linux ランナーでも回せる。
- **CI に AWS の認証情報を置かない**。自動テストは実際の AWS に接続しない構成にする（次節）。
- 「PR を経由せず `main` に直接 push してよいか」（リードの論点 1）の答えによって、マージ前ゲートが効くかどうかが決まる。直接 push を許すなら、ゲートは「push 後に CI が赤なら直ちに直す」という事後ルールになる点をインタビューで明示する。

### 5. Rust 製 GUI ＋ AWS SDK アプリのテストの型（提案）

品質側の推奨は「**GUI と AWS をどちらも外側に追い出し、真ん中のロジックを厚くテストする**」構成である。具体的な設計は後続の設計ステージで決めるが、テストしやすさのために開発ルールとして次を提案する。

- **層の分け方**：GUI に依存しないライブラリ（取得ロジック・状態管理）と、GUI のバイナリを分ける（Cargo ワークスペースで別クレートにする、など）。ライブラリ側は GUI フレームワークに依存しない。
- **AWS 呼び出しの境界**：ロググループ一覧・ストリーム一覧・GetLogEvents を呼ぶ部分を、アプリ側で定義した小さなインターフェース（trait）の裏に置く。ロジック層のテストはこの trait の **スタブ／フェイク** を使う（自分が所有していない SDK の型を直接モックしない）。
- **AWS 接続層そのもののテスト**：SDK が用意するテスト用の仕組み（`aws-smithy-mocks` や、記録した HTTP 応答を返すテスト用クライアント）で、実通信なしに「リクエストに終了時刻が入っているか」「スロットリング応答を受けたときの扱い」を確認する。
- **実際の AWS を使う確認**：自動テストには含めない。必要なら、環境変数が設定されたときだけ動く無効化済みテスト（`#[ignore]`）か、手元で実行する確認手順として分ける。
- **時間に依存する処理**：再試行の待機は、時計や待機処理を差し替えられるようにして、テストで実際に待たない（非同期ランタイムの時間停止機能など）。テストが遅くなる・不安定になることを防ぐ。
- **特に重点的にテストすべき点**（`initiative-brief.md` の取得要件から）：
  - ページ終端の判定：GetLogEvents は、渡したトークンと同じ `nextForwardToken` が返ったら終わり。この判定漏れは **無限ループ** になるため、必ず単体テストで押さえる。空ページが続くケースも含める。
  - 終了時刻を必ず指定すること（未指定でリクエストしないこと）。
  - スロットリング時の待機と再試行：回数上限と、上限を超えたときにエラーとして利用者に見えること（黙って失敗しない）。SDK 標準の再試行に任せるか、アプリ側で再試行するかは設計で決め、どちらでもテストで確認する。
  - ストリームを跨いだ時刻順マージ：出力が時刻順であること、件数が入力の合計と一致すること、同時刻の並び順が決まっていること。これらは性質ベースのテスト（`proptest` など）に向く。
  - タイムゾーン変換：切り替えても同じ瞬間を指すこと、夏時間の切り替わり（存在しない時刻・重複する時刻）の扱い。
  - 部分一致フィルター：大文字・小文字の区別、日本語などの非 ASCII 文字、空文字。
  - キャッシュ：既定で無効であること、有効時のみディスクに書くこと、削除で消えること。一時ディレクトリを使い、テスト同士でファイルを共有しない。
- **GUI 層**：画面の状態（取得中はボタン無効・Fetching 表示、取得中は条件変更不可、取得中の終了は確認）は、描画から切り離した **状態遷移** として表現し、その状態遷移を単体テストで確認する。これで `project.md` の学習済みルール（取得中の最低限の状態表示）も自動テストで守れる。描画そのものの自動テストは MVP では行わず、リリース前に手動の確認項目（起動・取得・絞り込み・終了確認）で補う案を提案する。
- **受け入れ条件との対応**：後続のユーザーストーリーの受け入れ条件（Given/When/Then）の ID を、テスト名またはテストのコメントに書いて対応を追えるようにする（Build and Test で受け入れ条件との対応を確認しやすくするため）。

### 6. 薄い一本（Walking Skeleton）を採用する場合の確認方法

- org.md では、骨組みの確認に「人間が承認した Construction Verification Command（プロジェクトの実際の端から端までの結果を示すもの）」を使う。リード下書きの「実際の AWS アカウントに対して GUI でログが表示できること」は **コマンドで自動判定できる形ではない**（GUI の表示を目で見る必要があり、実 AWS の認証情報も要る）。
- 次のどちらかに具体化することを提案する（インタビューで確認）：
  - **A.** 自動テスト（`cargo test --workspace`）に加え、手元で実 AWS に対して GetLogEvents を呼び結果を標準出力に出す小さな確認用プログラム（例：`cargo run --example smoke -- --profile <名前> --log-group <名前>`）を実行し、さらに GUI を起動して目視で確認する。
  - **B.** 自動テストのみをコマンドとし、実 AWS と GUI の確認は手動の確認項目とする（「実際の端から端までの結果」を示す力は弱くなる）。

### 7. インタビューで決めるべき論点（品質観点）

プロジェクトの学習済みルールに従い、**一問ずつ** 構造化質問で聞く。リードの論点 3 を次のように分けることを提案する。

1. テストの進め方：A `test-after` / B ロジック層だけ先にテスト（`custom`）/ C `tdd`。
2. カバレッジ下限：A 数値なし（ロジック層の公開関数にテスト必須）/ B GUI に依存しない層だけ 80% 行 / C 全体 80% 行 / 別の値。
3. マージ前に CI が通っていることを必須にするか（論点 1 の直接 push 可否とセットで聞く）。
4. 自動テストで実際の AWS に接続しないことを開発ルールにするか（ハードな制約として `discovered-rules.md` に残すかも含む）。
5. GUI の描画の自動テストを MVP で行うか（提案：行わず、状態遷移の単体テストと手動確認項目で補う）。
6. （薄い一本を採用する場合）確認コマンドの具体的な中身（6 節の A / B）。

## Positions

- AGREE: `## Testing Posture` の既定として `test-after` を提案する点。期限約 1 週間・個人開発に見合う。ただしロジック層だけ先にテストを書く `custom` 案も選択肢として示すべき。
- AGREE: テストの中心を GUI に依存しない層に置き、AWS 呼び出しを置き換える方針。加えて「アプリ側の trait の裏に AWS 呼び出しを置き、その trait をスタブにする」と具体化することを勧める。
- AGREE: `local-tool` が org.md のスコープ別下限に載っておらず、カバレッジ下限が未定であることをインタビューで確認するという整理。下限を書くと後で下げられないため、計測範囲（GUI 層を除くか）も同時に決めるべき。
- OBJECT: 「CI での実行は後続の CI ステージで設計する」として、マージ前に止めるチェックの種類まで先送りしている点。CI の実装は `ci-pipeline` の仕事だが、どのチェック（fmt / clippy / test / カバレッジ）が失敗したらマージを止めるかは開発ルールであり、この段階で決めて `team-practices.md` に書くべき。
- OBJECT: 薄い一本の確認方法を「実際の AWS アカウントに対して GUI でログが表示できることを示すもの」としている点。GUI の目視確認はコマンドで判定できず、実 AWS の認証情報も必要なため、自動部分（`cargo test`）と実 AWS・目視部分を分けて具体化すべき。
- AGREE: `discovered-rules.md` の確認候補をルールに昇格させず、人間が明言した場合のみ `ALWAYS` / `NEVER` にする扱い。品質観点では「自動テストで実際の AWS に接続しない」「CI に AWS の認証情報を置かない」も候補に加えることを勧める。
