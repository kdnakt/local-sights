# Team Practices（ドラフト）

> **ステータス: ドラフト（人間へのインタビュー前）**
> グリーンフィールドのため、本書の内容は `aidlc/spaces/default/memory/org.md` の既定値を、このプロジェクト（個人開発・GitHub 上の OSS `kdnakt/local-sights`・macOS 向け Rust 製デスクトップ GUI・ローカル実行のみ・MVP 目標 2026-10-10・スコープ `local-tool`）に合わせて読み替えた **提案** にすぎない。確定したチームの事実ではない。各項目はインタビューで確認し、最終統合で書き直す。

## Way of Working

（提案）私たちはトランクベース開発で進める。作業はすべて短命のフィーチャーブランチ（目安 1〜2 日以内）で行い、`main` にマージする。長く生きるブランチは作らない。

- Construction のワークツリーは `main` を基点とし、マージ先も `main` とする。
- Bolt ブランチは `main` にスクワッシュマージし、1 Bolt = `main` 上の 1 コミット（Bolt のスラッグ名）とする。
- 開発者は 1 人のため、PR は自分でマージする想定。セルフレビューで足りるか、PR を経由せず `main` に直接マージしてよい場面があるかは、インタビューで確認する。
- リリースは、長命のリリースブランチではなく `main` 上のタグで区切る（提案）。

## Walking Skeleton

（提案）まず最小の「端から端まで通る薄い一本」を作ってから、本格的な機能を足していく。

- このプロジェクトでの最小の一本は「起動した macOS の GUI ウィンドウから、選んだプロファイル・リージョン・ロググループ・時間範囲で GetLogEvents を呼び、結果を 1 画面に表示できる」こと（バックログの IB-00〜IB-04 を極小にしたもの）を想定する。
- 期限（2026-10-10）が短いため、最初に結線の不安（GUI フレームワーク・AWS SDK・認証）を潰す価値は高いと考える。一方、スコープ `local-tool` の定義には `skeleton` の指定がなく、採否はインタビューで決める。
- 採用する場合、骨組みの確認には人間が承認した Construction Verification Command（実際の AWS アカウントに対して GUI でログが表示できることを示すもの）を使う。

## Testing Posture

（提案）テストは各 Bolt の成果物の一部として扱う。org.md の既定（実装してからテストを書く）をそのまま提案する。

- **Methodology**: test-after
- **Ordering**: テスト可能な層ごとに、まずその層を実装し、続けてその層のテストを書いて実行する。
- テスト戦略は `Standard`（state 記録値）。テストの量と種類はこれに従う。
- スコープ `local-tool` は org.md のスコープ別テスト下限の一覧に含まれていないため、カバレッジ下限（例：`mvp` 等の 80% 行カバレッジ）を適用するかどうかは未定。インタビューで確認する。
- テストの中心は GUI に依存しない層（時刻順マージ、ページ終端判定、スロットリング時の待機・再試行、タイムゾーン変換、部分一致フィルター、キャッシュ）とし、AWS 呼び出しはモック／スタブで置き換える想定（提案）。GUI の自動テストは MVP では最小限とする想定。
- ツールは Rust 標準の `cargo test` を想定（提案）。CI での実行は後続の CI ステージで設計する。

## Deployment

（提案）このプロジェクトに「デプロイ」先のサーバーはない。org.md の「マージでステージングにデプロイ、本番は手動承認」はそのままは当てはまらず、ここでは「ローカルアプリの配布」と読み替える。

- AWS へのデプロイは行わない（decision-log D-03）。
- 配布は GitHub 上での OSS 公開を基本とし、`main` のタグを起点に GitHub Releases で macOS 向けビルド成果物を公開する案、または当面はソースからの `cargo build` / `cargo install` のみとする案がある。どちらにするかはインタビューで確認する。
- 本番相当の「承認」は、リリースタグを打つ判断を開発者本人が行うことに相当する（提案）。
- macOS のコード署名・公証（notarization）を MVP で行うかは未定。
- 「ロールバック」は、問題のあるリリースを取り下げ、前のタグのビルドに戻すことを指す（提案）。

## Code Style

（提案）プロジェクトの設定ファイルに従い、エージェントはそれを先に読む。

- フォーマッタ：`rustfmt`（言語標準。設定が必要ならリポジトリ直下の `rustfmt.toml`）。
- リンタ：`clippy`。警告の扱い（`-D warnings` で失敗させるか）はインタビューで確認する。CI ではマージ前に実行し、失敗したら PR をブロックする（org.md の既定）。
- 命名規則：Rust の慣用（関数・変数は snake_case、型は UpperCamelCase、定数は SCREAMING_SNAKE_CASE）。プロジェクト独自の改名ルールは設けない。
- フレームワークがスタイルを提案するのは、`rustfmt` / `clippy` が扱っていない点に限る。
