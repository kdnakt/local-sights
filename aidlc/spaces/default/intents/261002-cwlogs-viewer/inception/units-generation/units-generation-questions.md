## Q3. GUI フレームワークは何にしますか？

背景：薄い一本で GUI を動かすため、ここで決めます（技術選定は「開発ルール確認以降」に先送りしていました）。要件は、標準部品だけの見た目（NFR10）、100 万件の一覧をスクロールできること（NFR2）、キーボード操作（NFR13）、OS に合わせたダークモード（NFR11）、英日の表示（NFR12）、将来の Windows 対応（IB-16）です。

A. egui（eframe）：Rust だけで書ける。大量行の一覧を表示範囲だけ描く仕組みがある。OS のダークモードに追従できる。日本語の表示にはフォントの読み込みが必要。見た目は egui 独自（OS の部品そのものではない）
B. Tauri：画面は HTML/CSS/JavaScript、処理は Rust。日本語や OS らしい見た目を出しやすく、Windows 対応もしやすい。一方で JavaScript 側の開発環境（Node.js など）と、画面と Rust のやり取りの層が増える
C. Slint や iced など、その他の Rust 製 GUI

## F2. Tauri の画面側（HTML/CSS/JavaScript）の作り方とチェックはどうしますか？

背景：Q3 で Tauri を選んだ。開発ルールの Code Style は Rust（rustfmt・clippy）しか決めていない。見た目は標準部品だけ（NFR10）、100 万件の一覧を表示範囲だけ描く必要がある（NFR2）。

A. TypeScript と Vite だけを使い、画面のフレームワーク（React など）は使わない。CI で `tsc --noEmit`（型チェック）と Prettier のフォーマット確認を必須にする。大量行の一覧は表示範囲だけ描く仕組みを自前で作る
B. TypeScript と React を使う。大量行の一覧は既存の部品（仮想スクロールのライブラリ）を使う。CI で型チェックと Prettier・ESLint を必須にする
C. ビルドなしの素の JavaScript にする（チェックは入れない）
X. Other (please specify)

[Answer]: B. TypeScript と React を使う。大量行の一覧は既存の部品（仮想スクロールのライブラリ）を使う。CI で型チェックと Prettier・ESLint を必須にする

## Consolidated Summary Confirmation

回答のまとめ：

- 作業単位は 7 つ。薄い一本のあと機能ごとに分ける（Q1、F1）：
  - U1 薄い一本（u1-walking-skeleton）：プロファイルとロググループ名・ストリーム名を手入力し、開始・終了を UTC で入力して [Fetch] を押すと、1 つのストリームを GetLogEvents で最後のページまで取得して一覧表示する（Q2）

  - U3 取得の作り込み（u3-fetch-robustness）：複数ストリームの取得と時刻順の並べ替え、時刻によるストリームの選定、ページ終端、再試行、部分失敗、中断、逐次表示
  - U4 時間範囲とタイムゾーン（u4-time-range）：入力検証、TZ 切替、夏時間、終了境界
