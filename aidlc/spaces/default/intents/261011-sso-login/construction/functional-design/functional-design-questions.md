# Functional Design Questions — アプリから SSO ログインする

上流：`inception/requirements-analysis/requirements.md`（FR1〜FR4、NFR1〜NFR7）と、そのレビュー（`reviews/review-01.md`）で残った指摘。作業単位は 1 つで、既存のコード（`crates/local-sights-core` の catalog・gateway・session、`src-tauri/src/lib.rs`、画面の `LogGroupPane`・`FetchErrorBanner`）を設計の土台にします。

レビューの指摘のうち、利用者の判断が要らないものは次の既定で設計します（違えばゲートで直してください）。

- **「デフォルト」と AWS_PROFILE**：アプリの「デフォルト」は SDK の既定と同じく、環境変数 `AWS_PROFILE` があればそのプロファイル、なければ `[default]` を指す。SSO かどうかの判定もその同じプロファイルで行い、CLI はプロファイル指定なし・環境変数はそのまま引き継いで起動するので、CLI と SDK が同じプロファイルを使う。
- **ボタンが 2 か所に出る場合**：一覧のエラーと取得のエラーの両方に出ても、押せるログインは 1 つ。どちらかで始めると、両方の待機表示が同じログインの状態を示す。
- **画面に出す CLI の出力**：許可リスト方式とする。`https://` で始まる URL と、確認コードの形（英大文字 4 字・ハイフン・英大文字 4 字）に合う文字列だけを出し、それ以外の行は捨てる。どちらも見つからなければ「ブラウザで承認してください」の案内だけを出す。
- **CLI の探索順**：`/opt/homebrew/bin/aws`、`/usr/local/bin/aws` の順に、実行できるファイルがあるかを見る。
- **ログイン後の認証情報**：成功したら、そのプロファイルの SDK のクライアントを捨てて作り直す（再起動なしで新しいトークンを使わせるため）。

## Q2. 会社の SSO のプロファイルは、どの形ですか？

`aws sso login` でログインできるのは、SSO の設定（`sso_session` または `sso_start_url`）を直接持つプロファイルです。SSO のプロファイルを元に別のロールを引き受けるプロファイル（`source_profile` で SSO のプロファイルを指すもの）は、そのままではログインできません。

- A. SSO の設定を直接持つプロファイルだけを使っている
- B. SSO のプロファイルを元に AssumeRole するプロファイルも使っていて、それを選んだときもログインしたい（元の SSO のプロファイルでログインする）
- C. 分からない（直接持つプロファイルだけを対象にし、それ以外ではボタンを出さない）
- D. Not applicable
- X. Other (please specify)

[Answer]: B. SSO のプロファイルを元に AssumeRole するプロファイルも使っていて、それを選んだときもログインしたい（元の SSO のプロファイルでログインする）
