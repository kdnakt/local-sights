# Intent Statement — アプリから SSO ログインする

## Problem Statement

- アプリの中から SSO ログインできるようにしたい。進め方は「1の方向性」とする。[desc]
- 「1の方向性」とは、アプリが手元の AWS CLI のログイン（`aws sso login --profile <名前>`）を起動し、ブラウザでの承認・SSO の API 呼び出し・トークンの保存はすべて CLI が行う方式である。アプリ自身は SSO の API を呼ばず、トークンにも触れない。これは利用者が指定した前提条件として扱う。[Q2]
- SSO が切れたときに困っているのは次の 4 つである。[Q1]
  - アプリとターミナルを行き来して `aws sso login` を打つのが手間であること。[Q1]
  - どのプロファイルでログインし直すかを毎回考え、プロファイル名を打ち間違えること。[Q1]
  - 朝いちばんや長い休憩のあとなど、SSO が切れるたびに作業が止まること。[Q1]
  - ターミナルを開かずにアプリの中だけで完結させたいこと。[Q1]

## Target Customer

- 主な利用者と決定者は開発者本人である。[Q5]
- 利用者が得る価値は、SSO が切れても、アプリから離れずにログインし直して作業を続けられることである。[Q1] [Q4]

## Initiative Trigger

- SSO が切れるたびにターミナルとの行き来が必要で、作業が止まることがきっかけである。[Q1]

## 禁止ルールとの関係

- project.md の禁止ルールには、CloudWatch Logs の読み取り API 以外を呼ばないこと [memory:M2] と、SSO のトークンなどをキャッシュファイル等に書き込まないこと [memory:M1] がある。[memory:M1] [memory:M2]
- 「アプリが CLI のログインを起こすこと」は、これらのルールの趣旨の範囲内とする。誤解がないよう、ルールの文面に「CLI の起動は対象外」という補足を足したい。[Q3]

## Initial Scope Signal

- workflow-selected scope：`refactor`（このワークフローの進め方のもとになったもの）。[scope]
- user-confirmed product boundary（今回の成果物に入れないもの）：[Q6]
  - アプリ自身が SSO の API を直接呼んでログインする方式は作らない。[Q6]
  - SSO 以外の認証（アクセスキー、`credential_process` など）のログイン補助は作らない。[Q6]
  - プロファイルの作成や `~/.aws/config` の編集はアプリから行わない。[Q6]
  - ログインの状態を常に監視して、切れる前に知らせる仕組みは作らない。[Q6]
