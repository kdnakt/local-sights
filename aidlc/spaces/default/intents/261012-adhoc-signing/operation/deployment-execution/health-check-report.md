# Health Check Report — リリースの .app をアドホック署名する

## 対象

サーバーや常駐サービスはなく、監視対象のエンドポイントもない。「ヘルスチェック」に相当するのは、配布の仕組み（Release ワークフロー）が健全であることと、配られたアプリが利用者の Mac で起動することの 2 つ。

## 配布の仕組みの健全性（この時点で確認できたもの）

| 項目 | 確認方法 | 結果 |
|---|---|---|
| `release.yml` が YAML として正しく、step の順序が要件どおり | `yaml.safe_load` で step 名を列挙（Build and Test） | 正常 |
| 要件を機械的に確かめるテスト | `npx vitest run scripts/release/signing.test.ts` 24 件 | 正常 |
| 版の整合 | `npm run check:version -- --tag v0.1.1` | 正常 |
| 秘密情報の不使用 | `release.yml` の差分に `secrets.` の参照なし | 正常 |
| PR の CI（`ci.yml` の 5 ジョブ） | PR #18 のチェック | 実行中（マージの前提） |
| Release ワークフローの署名検証ステップ | タグ `v0.1.1` の実行ログ | 未（タグ打ち後） |

## 配られたアプリの健全性（公開後に開発者が確認）

`smoke-test-results.md` の S3〜S8。特に S3（「壊れている」が出ないこと）と S5（ターミナルなしで起動すること）が、この変更の成否を決める。

## 継続的な監視

- 新しいリリースのたびに Release ワークフローの署名検証ステップが通ること（失敗すれば Release は作られないので、ワークフローの失敗通知がそのまま検知になる）。
- macOS の大きな更新（毎年秋）のあと、初回起動のダイアログの種類が変わっていないかを `docs/install.md` の手順で確かめる。変わっていたら手順書を直す。

## エスカレーション

開発者 1 人のプロジェクトのため、エスカレーション先はなし。会社のルール（MDM で未公証アプリを拒む等）に当たった場合は、配布を止めて Developer ID と公証の導入を別の作業として検討する。
