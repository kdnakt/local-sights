# Rollback Runbook — リリースの .app をアドホック署名する

## 方針

署名付きの版に問題があっても、**署名なしの版（`v0.1.0`）には戻さない**。直した版をパッチとして出し、前に進む（Q2 の回答）。理由：`v0.1.0` に戻すと利用者はまた「壊れている」ダイアログと `xattr` の操作に直面し、戻すこと自体が今回直したかった問題を再発させるため。

team.md の「戻し方：前の版の `.dmg` を入れ直す」は、署名付きの版どうし（`v0.1.1` 以降）の間では従来どおり有効。署名なしの版への後戻りだけを例外とする。

## 事象ごとの対応

### 1. Release ワークフローの署名検証ステップが失敗した

- 影響：Release は作られていない。利用者には何も届いていない。
- 対応：
  1. Actions のログで `::error::` の文言を確認する（`has no valid signature` なら `APPLE_SIGNING_IDENTITY` の欠落か Tauri の挙動変更、`not ad-hoc` なら想定外の署名 ID）。
  2. PR で直し、CI を通してマージする。
  3. 同じタグを動かすか（`docs/releasing.md` の「When something fails」）、次のパッチ版を出す。Release が存在しない失敗タグは動かしてよい。
- 戻す操作：不要。

### 2. 公開後のスモークテストで「壊れているため開けません」が出た

- 影響：Release は公開されているが、まだ会社の Mac には配っていない（`deployment-strategy.md` の手順 5 は スモークテストの後）。
- 対応：
  1. 会社の Mac に配らない。配布の案内を止める。
  2. GitHub Releases のその版を **編集して下書き（draft）に戻すか、ノートの先頭に「配布中止」と書く**。タグとアセットは証跡として残す（削除しない）。
  3. 原因を調べる（`.dmg` から取り出した `.app` に `codesign -dvv` を実行し、`Signature=adhoc` と `codesign --verify` の結果を確認する。署名があるのにダイアログが出るなら、Gatekeeper 側の前提（A1）が崩れている）。
  4. 直して次のパッチ版（`v0.1.2`）を出す。A1 が崩れている場合は、`docs/install.md` の `xattr` の予備手順を主手順に戻すか、インストールスクリプトでの配布（隔離属性を付けない経路）を別の作業として検討する。
- 戻す操作：なし（前に進む）。

### 3. 会社の Mac に配ったあとで、署名付きの版に別の不具合が見つかった

- 影響：利用者が使っている。
- 対応：
  1. 不具合がアプリの振る舞いなら、直した版をパッチとして出す。署名の仕組みは変えない。
  2. 利用者には `docs/install.md` の「Update to a new version」の手順で置き換えてもらう。設定とキャッシュは残る。
  3. `v0.1.1` 以降の署名付きの版どうしであれば、team.md のとおり前の版の `.dmg` を入れ直す選択肢もある（`docs/install.md` の「Go back to an earlier version」）。`v0.1.0` には戻さない。
- 戻す操作：署名付きの前の版への入れ直し（利用者の操作）。

### 4. 署名付きの版に戻すことがどうしても必要で、署名付きの前の版がない（`v0.1.1` が最初の署名付き版のとき）

- 対応：前に進む（パッチ版）。それも間に合わない緊急時だけ、`docs/install.md` の予備手順（`xattr -dr com.apple.quarantine`）を添えて `v0.1.0` を案内する。これは例外であり、恒常的な戻し先にはしない。

## 証跡

- 配布を止めた Release は削除せず、ノートに「配布中止」と理由を書いて残す。
- 対応の記録は、この作業の記録（`aidlc/spaces/default/intents/261012-adhoc-signing/`）または次のパッチの PR に残す。
