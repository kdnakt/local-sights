## 主な実装の判断

- 中断でも閉じるでも、出ている呼び出しは待たずに打ち切る。打ち切った呼び出しは要約の calls に数えない
- 途中の更新（TauriSink の途中の view）が cancel_fetch の view より後に届き、［中断］が一時的に押せる見た目に戻ることはありうる。終わりの view で必ず直り、その間に押しても request_cancel が何もしないので許容する（非機能設計 R-08）
- 注意のアイコンのラベルには `status.cancelled`（Cancelled／中断）を使い、新しい文言キーは足していない。状態行の「中断」は StatusIndicator の `stopped`
- 契約 C5 の `cancelNotice`・`cancelling`・`fetchCancelAvailable` は契約どおりの形

## 計画からのずれ

1. 閉じるときの今のテスト `u1_concurrent_fetch.rs` の `pages_that_arrive_after_the_close_are_dropped` は、閉じるときに出ている呼び出しの応答を待つことを確かめていた（`timed_calls().len() == 2`、`elapsed >= 584ms`）。Q1 の決め（中断でも閉じるでも打ち切る、非機能設計で確定）に合わせ、呼び出しは 2 本始まっていた・どちらの応答も待っていない・閉じた時刻（100ms）に終わる、を確かめる形に直した。Aborted・0 件・バッチなし・ストリームの終わりなし・一覧が空のアサーションはそのまま
2. 形だけの直し：`fetch_status` の値のテストは ALL が 6 つになったので `ALL[..5]` を同じ 5 語と比べる。今の `decide_job_status` のテストは新しい引数に直した（期待する結果は同じ）
3. `streams/planner.rs` を変えた（設計どおりの実装場所）
4. 保存の始まり（on_saving）は軽い `fetch-progress` でしか画面に届かないため、`api.ts` の withProgress で cacheSaving が立ったら fetchCancelAvailable を false にした（R-09・BR5.2 のとおり保存中は押せない）。App のテストで確かめる
5. N の例（20 本、1,000 本）は結合テストに書いた（schedule.rs は変えないため）
6. `cargo doc` で doc コメントの `[Cancel]` がリンク先のない警告になる。既存の retry.rs・session.rs と同じ書き方で、`cargo doc` は CI のチェックに入っていない
