> R-01 Reviewer note: BR5.2 が fetchCancelAvailable の式（段階 Fetching かつ cancelling でなく cache_saving でなく閉じる確認の途中でない）を定め、判定元を既存の cache_saving に置いた。serve_from_cache は同期で進むので押せる間がないことも書いた。BR5.5 は、キャッシュを引いている間の Cancel を、当たれば serve_from_cache を最後まで通して Completed、当たらなければ run_fetch の一覧の前の Cancel と定め、Close は今のとおり Aborted とした。functional-spec 1.6 と 2 節の表も同じ内容で、serve_from_cache と abort の分岐も BR5.5 の対象に挙がっている。coordinator.rs の look_up は on_started より前なので、この間も phase は Fetching で押せるという前提も今のコードと合う。

> R-02 Reviewer note: BR5.4 と functional-spec 1.2 に、止めた後に届く応答の表が入った（最後でないページ、最後のページ、失敗、再試行や許可の待ち。理由 Cancel と Close の列つき）。止めた後は使い切りの数えを止めて Skipped を作らないことも明記された。理由 Close は今のとおり捨てる。ReadStage::run の continue 分岐を理由で分ける形になっており、実装の入口は定まった。残る細かい点は新しい指摘にまとめた。

> R-03 Reviewer note: BR5.5 が、run_fetch の is_stopped() の分岐を理由つきに置き換えること、decide_job_status の入力（止めた理由、一覧の結果、失敗の本数、N）、Cancel で N が 0 のときは Aborted にならず今と同じ決め方で on_finished とキャッシュの判定（BR5.7）に進むことを書いた。functional-spec 1.4 の手順 3 にもキャッシュ判定の流れがある。現在の decide_job_status(aborted: bool, ...) の引数を変える必要はここで読み取れる。
