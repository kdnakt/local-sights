# Scope Definition Questions — ロググループ全体の取得の高速化

ここまでに決まったこと：

- 含める：ロググループ全体の取得を速くする、取得の進み具合の表示、取得の中断（intent-statement）
- 含めない：Logs Insights 互換のクエリ、利用者による速さの設定（intent-statement）
- 保つ：利用者から見たキャッシュの動き（intent-statement）
- 使ってよい量は呼び出しの上限の半分程度、制限を受けたら引き下がる、中断したら取れた分は残す、「3 本続いたらあきらめる」決まりは決め直してよい、期限は 1 週間以内（feasibility）

今回の項目の候補（以下の質問で使う）：

- B1. 複数のストリームを同時に読んで、取得を速くする
- B2. 制限を受けたら、同時に読む量を減らすなどして引き下がる
- B3. 「3 本続いたらあきらめる」決まりを、同時に読む形に合わせて決め直す
- B4. 取得の進み具合を表示する
- B5. 取得を中断できるようにする（取れた分は残し、中断したことと取れていない範囲を示す）
- B6. 作り始める前に、いまの版の速さを手元で測っておく

## Follow-up Questions

## Q4. いまの速さとの比較（B6）は、今回どう扱いますか？

背景：Q1 では B6 を「欠かせない」に選ばず、Q3 では「測るのは最後に回す」を選びました。最後に測ること自体は今回に含めるのか、今回は測らないのかを確かめます。いまの版と比べるには、いまの版（変更前の版）で測った値が要ります。最後に測る場合も、変更前の版を手元で動かして同じ条件で比べることはできます。

A. あるとよい（Should）：最後に、変更前の版と新しい版を同じ条件で手元で比べる。期限が厳しければ外す
B. 欠かせない（Must）：最後に必ず比べ、「速くなった」を確かめてから完了とする
C. 今回は測らない（体感で十分）
D. Not yet defined
X. Other (please specify)

[Answer]: C

## Q5. 「速くなった」をどう判断しますか？

背景：Q4 で「今回は測らない（体感で十分）」を選びました。一方、意図の把握では成功の目安を「全件がそろうまでの時間が目に見えて短い（例：半分以下）」「最初の 1 件が出るまでの時間が短い」としています。測らない場合、この目安をどう確かめるかを決めます。

A. 体感で判断する：困りごとの場面のロググループを変更前と変更後で開き、明らかに速いと感じれば成功とする。成功の目安から数値の例を外す
B. 進み具合の表示に、取得にかかった時間も出す。その表示を見て判断する（変更前の版との厳密な比較はしない）
C. やはり最後に変更前の版と比べて測る
D. Not yet defined
X. Other (please specify)

[Answer]: B
