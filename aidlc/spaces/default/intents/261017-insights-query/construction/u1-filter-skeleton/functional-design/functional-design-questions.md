## 要件の見直し（RA Q3b）による整理（2026-10-18）

Q7a に答える途中で要件分析に戻り、2 つの画面は取得済みのログを共有しないと決めた（RA Q3b）。U1 のクエリの画面の取得は QueryStore（クエリの画面専用の保持）に入り、ログ管理の画面の保持には触れない（units Q2a）。そのため、Q1・Q7・Q7a が前提にしていた「ログ管理の画面のログが入れ替わる」「クエリの結果の指す先がなくなる」はどちらも起きなくなり、3 つの問いは不要になった。答えはそのとき記録したまま残す。Q2〜Q6 の答えは見直しの影響を受けないため、そのまま使う。

## Q1. U1 では、クエリの画面で取得すると Log Management の画面の表示中のログも入れ替わります（U3 までの暫定の動き）。これを利用者にどう示しますか？

A. Log Management の画面に表示中のログがあるときだけ、クエリの実行の前に確認ダイアログを出す（「Log Management の画面のログが入れ替わります」）。接続を変えるときの確認と同じ作り（推奨）
B. 確認は出さず、Log Management の画面の上に「Log Analytics で取得したログを表示しています」と示す
C. 何も示さない（U3 までの短い期間のため）
D. Not yet defined
X. Other (please specify)

[Answer]: C. 何も示さない（U3 までの短い期間のため）

## Q2. `filter` で `@timestamp` を比べるとき、どんな書き方を受け付けますか？

背景：FR1.5 で、文の中の `@timestamp` の条件は結果を絞ると決めています。利用者の依頼で調べた結果は次のとおりです。

- AWS の資料（Datetime functions）：「CloudWatch Logs Insights は、人が読める形の日時でログを絞ることには今は対応していない」。公式の例は `filter toMillis(@timestamp) >= (now() * 1000 - 7200000)` のように、`toMillis` でミリ秒の数値にしてから比べている
- AWS re:Post：`filter @timestamp >= '2020-06-01T00:00:00.000+00:00'` は動かなかったという報告がある
- `@timestamp` をそのまま数値と比べる書き方（`@timestamp > 1760659200000`）は、資料に書かれていない

A. `toMillis(@timestamp)` と数値の比較だけを受け付ける（公式の例と同じ書き方。FR5.5 の「関数は対応しない」の例外として `toMillis` の 1 つだけを足す。`now()` は対応しない）（推奨）
B. A に加えて、`@timestamp` をそのまま数値と比べる書き方も受け付ける（コンソールで動くかは U4 で確かめる）
C. U1 では `@timestamp` の比較を作らず、後の作業単位に回す（期間の欄で足りる）
D. Not yet defined
X. Other (please specify)

[Answer]: B. A に加えて、`@timestamp` をそのまま数値と比べる書き方も受け付ける（2026-10-18 に `timestamp-check.sh` でコンソールの動きを確かめ済みのため、U4 での確かめは要らない）

## Q2a. `@timestamp` を日時の文字列と比べる書き方（`filter @timestamp > "2025-08-24 16:43:26"`）を、アプリではどう扱いますか？

背景：Q2 の確かめで、コンソールでは日時の文字列と ISO の文字列のどちらとの比較も、エラーにならずに 0 件になると分かった。利用者から「タイムスタンプに内部的に変換して実行できるか」と聞かれ、できること、ただしコンソールと結果が変わること（「コンソールと同じ」の要件と D18 の互換の確かめから外れる）、タイムゾーンのない文字列の読み方と受け付ける書き方を決める必要があることを伝えた。

A. コンソールと同じく、何も示さず 0 件を返す
B. コンソールと同じく 0 件を返し、「`@timestamp` は数値（ミリ秒）と比べてください」という注意を結果の上に出す（推奨）
C. コンソールにない拡張として、文字列をミリ秒に直して比べる。タイムゾーンのない文字列は画面で選んでいるタイムゾーン（FR1.4）で読む。受け付けるのは Q2 で試した 2 つの書き方（`YYYY-MM-DD HH:MM:SS.sss` と `YYYY-MM-DDTHH:MM:SS.sssZ`）だけにし、要件に書き足す
D. Not yet defined
X. Other (please specify)

[Answer]: C. コンソールにない拡張として、文字列をミリ秒に直して比べる。タイムゾーンのない文字列は画面で選んでいるタイムゾーン（FR1.4）で読む。受け付けるのは Q2 で試した 2 つの書き方だけにし、要件に書き足す

## Q4. 重すぎるクエリへの備え（ADR-002）として、クエリの文の長さに上限を設けますか？

背景：正規表現は利用者の文から作ります。このアプリが使う正規表現の仕組みは、入力の長さに比例する時間で一致を調べるため、極端に遅くなる書き方は起きません。残る心配は、とても長い文や大きな正規表現でメモリを多く使うことです。コンソールに渡せるクエリの文は 10,000 文字までです（StartQuery の queryString の上限）。

A. コンソールと同じく 10,000 文字までにする。超えたら実行を押せなくし、理由を示す。正規表現の大きさの上限は仕組みの既定のままにし、超えたらエラーにする（推奨）
B. 文の長さの上限は設けず、正規表現の大きさの上限だけにする
C. Not yet defined
X. Other (please specify)

[Answer]: A. コンソールと同じく 10,000 文字までにする。超えたら実行を押せなくし、理由を示す。正規表現の大きさの上限は仕組みの既定のままにし、超えたらエラーにする

A. ミリ秒は省いてよい。省いたときはその秒の 0 ミリ秒とする（Q2a の例がそのまま使える）（推奨）
B. ミリ秒ありの 2 つの書き方だけを受け付ける（Q2a の答えの文面どおり）
C. Not yet defined
X. Other (please specify)

[Answer]: A. ミリ秒は省いてよい。省いたときはその秒の 0 ミリ秒とする

## Q7. U1 では、クエリの結果を出したあとに Log Management の画面で取得し直すと、クエリの結果が指すログが入れ替わります。クエリの結果をどう扱いますか？

C. 結果に出たイベントを写して持ち、取得し直しても結果を残す（メモリが増える）
D. Not yet defined
X. Other (please specify)

[Answer]: D. Not yet defined
