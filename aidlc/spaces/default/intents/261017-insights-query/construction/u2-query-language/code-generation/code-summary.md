## 速さの測り（Step 17、NFR1、OQ3）

`cargo test --release -p local-sights-core query:: -- --ignored --nocapture`（開発用のコンテナの Linux、1 回の実行）。取得済みのイベントは 8 つのストリームにまたがり、9 割が JSON のオブジェクト（level・入れ子の http.status・latency）、1 割が JSON でない文。「最も長い 1 区切り」は、止める信号を 2 回確かめる間の時間で、[Cancel] が効くまでの遅れの上限にあたる。

| クエリ | 10 万件 | 100 万件 | 100 万件の最も長い 1 区切り | 100 万件の matched／rows |
|--------|---------|----------|-----------------------------|--------------------------|
| filter だけ（`filter @message like /ERROR/`） | 20.9 ms | 252.6 ms | 188.8 ms | 142,858／10,000 |
| JSON の項目の filter（`filter level = 'ERROR' and http.status >= 500`） | 67.5 ms | 731.0 ms | 180.3 ms | 11,689／10,000 |
| JSON の項目の sort（`sort latency desc`） | 122.8 ms | 1.61 s | 707.5 ms | 1,000,000／10,000 |
| fields・filter・sort・limit（`limit 100`） | 80.6 ms | 1.12 s | 414.3 ms | 128,572／100 |

- 並べ替えの間の [Cancel]（R-02）：100 万件の JSON の sort で、最も長い 1 区切り（鍵だけの並べ替えで、止められない部分）は 819 ms だった（上の表とは別の実行）。3 つの区切りのあとで止める信号を立てると、結果を出さずに止まった（そこまで 489 ms）。
- 100 万件の filter だけで最も長い 1 区切り（約 190 ms）は、最初の並び（@timestamp の降順）を決める部分。
- 合否の数値は決めていない。この結果を見て Build and Test で人と決める（project.md の Testing Posture のとおり。決めた数値は下げない）。

## 仮の決まりと U4 に引き継ぐ確かめ

コンソールで確かめていない組は、BR1.6 などのとおりに作り、コードの説明とテストの名前（`provisional_…`）に仮の決まりと書いた。U4 でコンソールの結果と比べる。

- **R-01（型の比べ方）**：`crates/local-sights-core/src/query/evaluator.rs` の `ordering`・`as_text`
  - 数字だけの文字列と数の `<`・`>`（`=` は 6b で確かめた）
  - 数字でない文字列どうしの順序（Unicode の順にした）→ Loop-back 2 で確かめた決まりに直した（下の「Loop-back 2」）
  - 真偽値は文字列の `true`／`false` として比べる（`= "true"` は Loop-back 2 の前の互換の確かめで確かめた。出し方は 1／0 に直した）
  - JSON の数と文字列 "200" の実値の比べ（数として比べる）
  - JSON の数と真偽値を like・`=~` で見るときは書いたとおりの文字列
  - 6a（文字列の項目と数の項目の比べ）は、アプリが項目どうしの比べを作らないため起きない → Loop-back 2 で項目どうしの比べに対応したため、今は書ける（下の「Loop-back 2」の残る仮の決まり）
- **R-03（大文字・小文字）**：`crates/local-sights-core/src/query/parser.rs`。AND・OR・NOT・NOT LIKE・NOT IN も区別せずに読む。確かめたのは FILTER・LIKE・IN・Fields・Sort・Desc・Limit だけ
- **R-04（`limit 0` と既定の上限）**：`crates/local-sights-core/src/query/plan.rs` の `has_row_limit`。`limit 0` は limit による絞りなしで、既定の上限 10,000 は別に効く。10,000 件を超えるロググループでの確かめは U4 → Loop-back 3 で確かめた決まり（`limit 0` は 0 行）に直した（下の「Loop-back 3」）
- **そのほか（project.md の Corrections に記録済み）**：`not` の位置の規則以外の優先順位、`sort` がないときの並び（@timestamp の降順にした）、`@log` の値はロググループ名だけ（`@log` の値を比べるクエリは互換の確かめの組に入れない）
