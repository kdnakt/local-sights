## 質問にしなかったこと

U3 で決めることは、要件・ドメイン設計・今のコードで答えが決まるか、要件がどちらでもよいとしているものだけだった。利用者に判断してもらう問いはないため、決めたことと根拠をここに書く（違えば、承認の計画のときに直す）。

| 決めたこと | 根拠 |
|---|---|
| 一部のストリームが失敗したロググループと、[Cancel] で止めたロググループは、その実行で取れた分を結果には使うが、取得済みの範囲には加えず、次の実行を始めるときに捨てて取り直す | FR2.5（失敗した部分は取得済みとみなさない）、FR2.6（止める前の分は取得済みとして残して「よい」）。残すと、同じ範囲を次に取り直したときに同じイベントを 2 回持つ（ADR-004 の前提が崩れる）。捨てれば ADR-004 のとおり範囲が重ならない |
| ロググループは 1 つずつ順に取得し、1 つのロググループの中は今と同じく 8 本まで同時に読む | 今の取得の流れ（StreamPlanner・EventFetcher・CallPacer）をそのまま使える。呼び出しの速さの上限はリージョンごとに 1 つで、ロググループを並べても速くならない |
| 取得済みの範囲の新しさ：取得を始めた時刻から 5 分前より新しい部分は、取得済みの範囲に加えない（次の実行で取り直す） | 今のディスクキャッシュの決まり（record_range：取得の直前 5 分は記録しない、U6）と同じにする。遅れて届くログを取りこぼさないため |
| キャッシュの記録範囲は、足りない範囲と重なる部分だけを読んで使う | FR2.2。今の lookup は要求の全体を含む範囲しか使わないため、重なる部分を切り出す照会を足す（ドメイン設計の R-02） |
| ストリーム内の順番は、QueryStore に足すときに、ストリームごとに続きの番号を振り直す | ADR-004、ドメイン設計の R-05。今の EventTimeline はストリームごとに 0 から隙間のない番号を前提にしている |
| 失敗したストリームの一覧に、ロググループの名前を添える | ドメイン設計の R-04。複数のロググループで同じ名前のストリームがある（FR2.8） |
| U2 のコードの見直しの R-01（条件の入れ子に上限がなく、深いとアプリが落ちる）は、この作業単位で直す。上限は括弧と not の入れ子で 100 段とし、超えたら書き間違いにする | アプリが落ちる不具合のため、次の作業単位（U3）で直す（project.md Corrections）。100 段はふつうのクエリでは届かず、スタックに十分な余裕がある |
