## 1. 意図の分析

- **何を達成したいか**：今の絞り込みは、メッセージに文字列を含むかどうかの条件を 1 つしか書けない。いちばん困っているのは、条件を組み合わせられないこと（例：「ERROR を含み、かつ timeout を含まない」）である。CloudWatch Logs Insights に似たクエリを書いて、ログを絞り込み・並べ替えられるようにする（intent-statement、意図 Q1）。
- **誰のためか**：開発者本人、同じ会社の同僚、OSS の利用者（意図 Q2）。
- **できたと言える目安**：マネジメントコンソールの Logs Insights で書いていたクエリが、このアプリが対応する範囲ではそのまま書けて、同じ結果になる（意図 Q3）。
- **種類と規模**：既存のアプリ（Rust の中核ライブラリ・Tauri・React）への機能追加。中核に新しいクエリの層を足し、画面に新しいクエリの画面を足す。今の部分一致の絞り込みとログの画面は残す（範囲の「変えないもの」、RA Q3）。
- **複雑さ**：Standard。クエリの読み取りと評価そのものは純粋な処理だが、複数のロググループと足りない分だけの取得は、今の取得とタイムラインの作り（取得のたびに保持中を捨てる、ロググループは 1 つ、取得済みの範囲を記録しない）とは別に、クエリの画面のための保持と取得済みの範囲の記録を要する。ログの画面の取得とタイムラインは今のまま変えない（RA Q3b）（codekb architecture の Key Design Decisions）。

## 2. 機能要件

### FR1. クエリの画面（B1〜B5、RA Q1・Q3）

- **FR1.1** アプリは、今のログの画面（Log events）とは別に、クエリの画面（Logs Insights）を持つ。2 つの画面は切り替えて使う（RA Q3）。
- **FR1.2** クエリの画面には、ロググループを選ぶ欄、期間（開始・終了）を入れる欄、クエリの文を書く欄、実行ボタン、結果の一覧、状態の表示を置く。配置と見た目は画面の詰め（Refined Mockups）で決める（RA Q1・Q3）。
- **FR1.3** ロググループは、今の接続（プロファイル・リージョン）で一覧できるもの（DescribeLogGroups）の中から、1 つ以上選べる（範囲 Q2、RA Q1）。
- **FR1.4** 期間は、今のログの画面と同じ決まり（絶対日時、秒まで、表示と入力のタイムゾーンの切り替え、終了はその秒の 999 ms まで含む、開始は終了より前）で入れる（261002 の FR3 と同じ、RA Q1）。
- **FR1.5** クエリの文には、ロググループと期間を書かない。書き方はコンソールの Logs Insights と同じにする（RA Q1）。文の中の `@timestamp` の条件は、ほかの条件と同じく `filter` の条件として結果を絞る。
- **FR1.6** 次のすべてを満たすときだけ、実行ボタンを押せる。満たさないときは押せない状態で、理由を文字で示す（261002 の FR3.4 にならう）。
  - 接続（プロファイル・リージョン）が選ばれている
  - ロググループが 1 つ以上選ばれている
  - 開始・終了が正しい形式で、開始が終了より前である
  - クエリの文が空白だけではない
  - そのクエリの画面で、実行中ではない
- **FR1.7** クエリは、実行ボタンを押したとき（とキーボードの決まった組み合わせを押したとき）だけ実行する。入力中に自動で実行しない（RA Q4）。キーの組み合わせは画面の詰めで決める。
- **FR1.8** 今のログの画面の部分一致の絞り込み（261002 の FR6）は、今のまま残す。クエリの画面には部分一致の欄を置かない（RA Q3）。

受け入れ基準：
- Given ロググループを 2 つ選び、期間とクエリを入れた When 実行ボタンを押す Then 2 つのロググループのログに対してクエリが実行され、結果が一覧に出る
- Given ロググループを 1 つも選んでいない When クエリの画面を見る Then 実行ボタンは押せず、ロググループを選ぶ必要があることが文字で示される
- Given クエリの文を書いている途中 When 入力を止める Then クエリは実行されない
- Given ログの画面で部分一致の文字列を入れている When クエリの画面に切り替えてクエリを実行する Then 部分一致の文字列はクエリの結果に効かず、ログの画面に戻ると同じ文字列と絞り込みが残っている

### FR2. クエリの画面の取得済みのログと、足りない分だけの取得（B5、RA Q3b）

- **FR2.1** 取得済みのログは、ログの画面とクエリの画面で共有しない。クエリの画面は、自分で取得したログだけを「取得済みの範囲」として持ち、範囲は（プロファイル, リージョン, ロググループ）ごとに持つ。ログの画面の取得と保持（取得のたびに保持中を捨てて取り直す）は今のまま変えず、ログの画面で取得したログはクエリの画面の取得済みとみなさない。クエリの画面の取得もログの画面の表示中のログを変えない（RA Q3b）。
- **FR2.2** クエリを実行すると、選んだロググループごとに、期間のうちまだ取得していない部分だけを、今と同じ読み取りの API（DescribeLogStreams・GetLogEvents）で取得してから、クエリを評価する（B5）。ディスクキャッシュが有効なら、キャッシュに記録された範囲も取得済みとして使う（ログの画面がキャッシュに書いた範囲も含む。キャッシュの書き込みの決まりは今と同じ）。
- **FR2.3** 期間がすべて取得済みのときは、AWS を呼ばずにクエリを評価する。
- **FR2.4** 取得は、今の取得と同じ決まり（同時に読む本数、呼び出しの速さの上限と引き下げ、再試行、あきらめの決まり）で行う。取得中は処理中であることを示し、[Cancel] で止められる（D15、project.md Corrections の最低限の状態表示）。
- **FR2.5** 取得の途中で一部のストリームが失敗したときは、取得できた分でクエリを評価し、結果が一部のログだけからできていることと、失敗したストリームを示す（261002 の「失敗したストリームは一覧に出して残りを表示する」にならう）。失敗した部分は取得済みとみなさない。
- **FR2.6** 取得を [Cancel] で止めたときは、クエリを評価せず、止めたことを示す。止める前に取得できた分は取得済みとして残してよい。
- **FR2.7** 同じストリームの別の期間を取り足したとき、同じイベントを 2 回数えない。1 つのイベントは結果に 1 回だけ出る。
- **FR2.8** 違うロググループに同じ名前のストリームがあっても、別のストリームとして扱う（codekb の懸念：ストリーム名の衝突）。

受け入れ基準：
- Given ロググループ A の 10:00〜11:00 を取得済み When A の 10:00〜12:00 でクエリを実行する Then 11:00〜12:00 の部分だけを取得してから、10:00〜12:00 のログに対してクエリが評価される
- Given ロググループ A の 10:00〜11:00 を取得済み When A の 10:15〜10:45 でクエリを実行する Then AWS は呼ばれず、結果が出る
- Given 取り足しで 10:59〜11:01 のイベントが既存の取得と重なる When クエリを実行する Then 重なったイベントは結果に 1 回だけ出る
- Given 2 つのロググループに同じ名前のストリーム `s1` がある When 両方を選んでクエリを実行する Then 2 つの `s1` のイベントはどちらも結果に出て、`@log` で見分けられる
- Given 取り足しの途中で 1 本のストリームが失敗した When 取得が終わる Then 取得できた分の結果が出て、一部のログだけの結果であることと失敗したストリームが示される
- Given ディスクキャッシュが切で、ログの画面でロググループ A の 10:00〜11:00 を取得して表示している When クエリの画面で A の 10:00〜11:00 でクエリを実行する Then クエリの画面は 10:00〜11:00 を AWS から取得してから評価し、ログの画面の表示中のログと絞り込みはそのまま残る

### FR3. クエリの命令（B1・B2・B4、意図 Q6）

- **FR3.1** 使える命令は `fields`・`filter`・`sort`・`limit` とし、`|` でつないで並べられる。書き方はコンソールの Logs Insights と同じにする（意図 Q6、RA Q1）。
- **FR3.2** `filter <条件>` は、条件を満たすイベントだけを残す（B1）。
- **FR3.3** `fields <項目>, ...` は、結果の一覧に出す項目（列）を選ぶ（B2）。`fields` を書かないときに出す項目は、コンソールと同じにする（Open questions の OQ2）。
- **FR3.4** `sort <項目> [asc|desc], ...` は、結果を項目の値で並べる。並び方を書かないときの向きはコンソールと同じにする（OQ2）。同じ値のイベントの順番は、決まった順（時刻、ロググループ、ストリーム、ストリーム内の順番）で決める（B4）。
- **FR3.5** `sort` を書かないときの結果の並び順は、コンソールと同じにする（OQ2）。互換を確かめるときは、`sort` を書かないクエリの並び順は比べない（D18）。
- **FR3.6** `limit <件数>` は、結果を先頭から指定の件数までにする（B4）。
- **FR3.7** `limit` を書かないときも、結果の件数はコンソールの Logs Insights と同じ上限までにする。上限の数は AWS の資料で確かめて決める（RA Q5、OQ1）。上限で打ち切ったときは、打ち切ったことを示す。
- **FR3.8** 命令の名前と、`and`・`or`・`not`・`like`・`in` などの言葉の大文字・小文字の扱いは、コンソールと同じにする（OQ2）。

### FR4. 項目（B3、範囲 Q1）

- **FR4.1** 決まった項目 `@timestamp`・`@message`・`@logStream`・`@log` を使える（B3）。`@log` はロググループを表し、複数のロググループを選んだときに見分けに使う。
- **FR4.2** メッセージが JSON のオブジェクトとして読めるイベントからは、その項目を自動で取り出して使える。入れ子の項目は `a.b` の形で指定する（B3）。
- **FR4.3** メッセージが JSON として読めないイベント、壊れた JSON のイベント、JSON の配列や文字列だけのイベントは、JSON の項目を持たないイベントとして扱う。エラーにはせず、ほかのイベントの評価を続ける（corner-checklist：壊れた記録が混じる）。
- **FR4.4** イベントにない項目を条件や並べ替えに使ったときの扱い（値がないときに条件がどうなるか、並べ替えで前に来るか後ろに来るか）は、コンソールと同じにする（OQ2）。
- **FR4.5** JSON の値の型（数値・文字列・真偽値・null）による比較の扱いは、コンソールと同じにする（OQ2）。

### FR5. `filter` の演算子（B1、RA Q2）

- **FR5.1** 比較 `=`・`!=`・`<`・`<=`・`>`・`>=` を使える（RA Q2）。
- **FR5.2** 組み合わせ `and`・`or`・`not` と括弧を使え、優先順位はコンソールと同じにする（RA Q2、OQ2）。
- **FR5.3** 文字列の一致 `like`（文字列と正規表現 `/.../`）、`=~`（正規表現）、`not like` を使える（RA Q2）。大文字・小文字の扱いと正規表現の書き方の範囲はコンソールと同じにする（OQ2）。
- **FR5.4** `in [値, ...]` と `not in [値, ...]` を使える（RA Q2）。
- **FR5.5** `ispresent`・`isempty` などの関数、文字列の関数、数値の関数は、最初の版では対応しない（RA Q2）。書いたときは FR6 のエラーにする。ただし `toMillis(@timestamp)` の 1 つだけは対応する（U1 の機能設計 Q2）。
- **FR5.6** `@timestamp` は、ミリ秒の数値（`toMillis(@timestamp)` と、`@timestamp` をそのまま書く形の両方）と比べられる。コンソールにない拡張として、日時の文字列とも比べられる。受け付ける書き方は `YYYY-MM-DD HH:MM:SS[.sss]`（画面で選んでいるタイムゾーンで読む）と `YYYY-MM-DDTHH:MM:SS[.sss]Z`（UTC）の 2 つで、ミリ秒を省いたときはその秒の 0 ミリ秒とする。それ以外の文字列と比べたときは、書き間違いとして取得の前にエラーにし、場所と受け付ける書き方を示す（U1 の機能設計 Q2・Q2a・Q5・Q6。コンソールでは日時の文字列との比較はエラーにならず 0 件になるため、この拡張を使ったクエリは互換の確かめ（SM1）の組に入れない）。

受け入れ基準：
- Given `ERROR` を含むイベントと、`ERROR` と `timeout` を両方含むイベントがある When `filter @message like /ERROR/ and @message not like /timeout/` を実行する Then 前者だけが結果に出る
- Given JSON のメッセージ `{"level":"error","http":{"status":500}}` を持つイベントがある When `filter level = "error" and http.status >= 500` を実行する Then そのイベントが結果に出る
- Given JSON ではないメッセージのイベントが混じっている When JSON の項目を使った `filter` を実行する Then エラーにならず、JSON の項目を持つイベントだけが条件で判定される
- Given `filter status in [500, 503]` When 実行する Then `status` が 500 か 503 のイベントだけが結果に出る
- Given 選んでいるタイムゾーンが Asia/Tokyo When `filter @timestamp >= "2025-08-25 01:43:26"` を実行する Then `@timestamp >= 1756053806000`（2025-08-24 16:43:26 UTC）と同じ結果になる
- Given `filter @timestamp > "yesterday"` When 実行ボタンを押す Then AWS は呼ばれず、受け付ける日時の書き方と、その場所がエラーで示される

### FR6. 対応外の書き方と、書き間違いのエラー（B7、範囲 Q8）

- **FR6.1** 対応外の命令（例：`stats`・`parse`・`dedup`）、対応外の関数、対応外の演算子を書いたクエリを実行すると、取得もクエリの評価もせず、画面のエラーで「対応していない」ことと、その言葉と、クエリの中の場所（行と列）を示す（B7）。
- **FR6.2** 書き間違い（閉じていない括弧や引用符、命令の後ろに何もない、など）も、取得の前にエラーにし、クエリの中の場所を示す。対応外と書き間違いは、別の文言で区別する。
- **FR6.3** エラーになっても、書いたクエリの文は消さない（corner-checklist：入力を残す）。
- **FR6.4** エラーの文言は英語と日本語を用意し、今の画面と同じく OS の言語設定に合わせる（261002 の NFR12）。エラーにはクエリの言葉と場所だけを出し、秘密の認証情報やアクセスキー ID は出さない（project.md Forbidden）。

受け入れ基準：
- Given `fields @message | stats count(*) by bin(5m)` When 実行ボタンを押す Then AWS は呼ばれず、`stats` に対応していないことと、その場所がエラーで示され、クエリの文は残る
- Given `filter (@message like /a/` When 実行ボタンを押す Then 括弧が閉じていないことと、その場所がエラーで示される

### FR7. 結果の表示（B2）

- **FR7.1** 結果の一覧には、`fields` で選んだ項目（書かないときは FR3.3 の項目）を列として出す。時刻の列は、今の画面と同じく選んだタイムゾーンで出す。
- **FR7.2** 結果が 0 件のときは、0 件であることを示す。取得や評価の失敗とは区別する（corner-checklist：空・読み込み中・エラーは別の表示）。
- **FR7.3** 結果の件数を示す。FR3.7 の上限で打ち切ったときは、そのことも示す。
- **FR7.4** 行を開くと、メッセージ全体を見られる（今のログの画面と同じ）。
- **FR7.5** 結果の件数が多くても、一覧のスクロールは今のログの画面と同じく滑らかに動く（261002 の NFR2 にならい、見えている行だけを読む）。
- **FR7.6** 実行中に新しいクエリを実行することはできない（FR1.6）。結果は、最後に実行したクエリのものだけを出す（corner-checklist：古い応答が後から届く）。

### FR8. 対応範囲の一覧（B6、範囲 Q8）

- **FR8.1** README に、対応する命令・項目・演算子の一覧と、対応しないもの（`stats` など、FR5.5 の関数）を短く書く。クエリの書き方の説明は書かず、AWS の資料に任せる（B6、scope-document の範囲外）。
- **FR8.2** README の「streams are read one after another」のように、今の動きと食い違う記述があれば、この一覧を書くときに合わせて直す（codekb の Improvement Opportunities）。

### FR9. クエリを書く手助け（B8〜B10、Should）

時間が足りないときは次の版に回してよい（範囲 Q9）。

- **FR9.1** 入力の補完：命令の名前、決まった項目、取得済みのログの JSON の項目の名前を候補として出す（B8）。
- **FR9.2** 構文の色分け：命令・項目・文字列・数値・正規表現を色で分ける。色だけで意味を伝えない（corner-checklist：状態を色だけで示さない）（B9）。
- **FR9.3** 例のクエリ：対応する範囲の例のクエリをいくつか選んでクエリの欄に入れられる（B10）。

| NFR1 | 性能 | クエリの実行の速さ | 今の部分一致の絞り込みの基準（取得済み 10 万件で 10 秒以内、100 万件で 100 秒以内）より遅くてよい。合否の数値と測る条件（クエリの種類、件数、測る機械）は、作る段階（Construction）で測ってから決め、決めた数値は下げない。測るのは取得の時間を含まない、実行ボタンからの評価の時間とする | RA Q6、RA Q6a、D15 |
| NFR2 | 容量 | 大量件数でも落ちない | 取得済み 100 万件に対してクエリを実行しても、アプリは落ちず、結果が出る。評価中も画面は操作に反応する | 261002 の NFR2、RA Q6 |
| NFR3 | 互換 | コンソールとの互換を確かめる | AWS の資料にあるクエリの例のうち、対応する範囲（FR3〜FR5）に入り、開発者の AWS アカウントにすでにあるロググループの形に合うものを、互換を確かめるクエリの組とする。各クエリについて SM1 を手元の確認用プログラムで自動で比べる。比べるのは行の集まりで、並び順は `sort` を書いたクエリだけ | D17〜D19、RA Q7 |
| NFR4 | 互換の確かめの安全 | 確認は手元だけで行う | 確認用プログラムは開発者の手元で、本人の AWS 認証情報で動かす。自動テストと CI からは AWS に接続しない。コンソールから書き出した結果はログの中身を含むため、リポジトリに置かない | project.md Forbidden、team.md Walking Skeleton、initiative-brief |
| NFR5 | セキュリティ | 読み取り専用 | 呼ぶ AWS API は DescribeLogGroups・DescribeLogStreams・GetLogEvents だけ。StartQuery などの Logs Insights の API は呼ばない | project.md Forbidden、[desc] |
| NFR6 | 動く OS | macOS と Windows | クエリの画面とクエリの評価は、macOS（Apple Silicon）と Windows 11（x64）で同じように動く。クエリの層は OS に依存しない純粋な処理にする | intent-statement、team.md Deployment |
| NFR7 | 保守性 | テストしやすい構成 | クエリの読み取りと評価は、GUI に依存しない中核ライブラリに置き、公開関数にはテストを書く。純粋なロジック（クエリの読み取り、評価、取得済みの範囲の計算）はテストを先に書く。AWS はテストで偽物に差し替える | team.md Testing Posture・Code Style |
| NFR8 | テストの網 | カバレッジを下げない | 中核ライブラリと画面の行カバレッジは、今と同じく 80% を下回らない。Rust のテストは Linux・macOS・Windows の各ランナーで通る | team.md Testing Posture |
| NFR9 | 表示言語 | 英語と日本語 | クエリの画面の文言とエラーは、英語と日本語を用意する | 261002 の NFR12 |
| NFR10 | アクセシビリティ | キーボード操作 | クエリの画面の主な流れ（ロググループを選ぶ → 期間を入れる → クエリを書く → 実行する → 結果を見る）を、キーボードだけで操作できる | 261002 の NFR13 |
| NFR11 | 見た目 | 標準部品 | 今の画面と同じ部品の集まり（Cloudscape）を使い、独自のデザインは作らない | project.md Corrections、261002 の NFR10 |
| NFR12 | 外部への送信 | 何も送らない | クエリの文や結果を外部に送らない。テレメトリやクラッシュレポートを送らない | project.md Forbidden |

## 5. 前提（Assumptions）

| ID | 前提 | 理由 |
|----|------|------|
| A1 | 「クエリの中で期間とロググループを指定する」（B5）は、クエリの画面に置く専用の欄で指定することと読み替える | コンソールと同じ書き方を保つため、利用者が文の外で指定することを選んだ（RA Q1） |
| A2 | クエリの画面とログの画面は同じ接続（プロファイル・リージョン）を使う。接続を変えたときは、今のログの画面と同じく、クエリの画面の取得済みのログと結果も捨てる | 接続はアプリに 1 つ（今の作り）。取得済みのログは画面ごとに持つが、範囲は接続ごとに分ける（FR2.1、RA Q3b） |
| A3 | 評価はすべてメモリの中の取得済みのログに対して行う。新しい保存の仕組み（データベースなど）は足さない | 今の作り（タイムラインとディスクキャッシュ）と同じ考え方で足りる見込み。同じログを両方の画面で取得すると、メモリには 2 つ分持つ（RA Q3b で受け入れた）。NFR1・NFR2 を測って足りなければ設計で見直す |
| A4 | 単一の利用者・手元の PC で動くアプリのため、権限・テナント・個人データの決まりは加えない | corner-checklist の使い方（配置の形を先に決める） |
| A5 | クエリの結果は、取得済みのログが後から増えても自動では作り直さない。作り直すのは実行ボタンを押したときだけ | 実行は実行ボタンだけ（RA Q4） |
