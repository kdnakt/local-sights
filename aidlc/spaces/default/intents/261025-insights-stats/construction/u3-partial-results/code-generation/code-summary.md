## 実装の主な決め方

- **並行の作り方（BR1.1）**
  - sink は `run_query` の本流だけが持つ。
  - 本流は `tokio::select!`（biased）で、取得の future・途中結果の `mpsc`・新しいページの `Notify`・1 秒の間隔の `sleep_until` を待つ。
  - ページを受けるたびに `FetchCounters`（`AtomicBool`・`AtomicU64`）に書き、途中の評価を始めるかどうかは副作用のない関数 `should_start_partial`・`next_partial_check` で決める。
  - 途中の評価は `spawn_blocking` で行う。止める旗・view の食い違い・panic（`catch_unwind`）のどれで終わっても、必ず 1 通だけ送る。
  - 取得が終わったら止める旗を立て、評価が終わるのを待ってから最終の view を作る。
  - `partial_interval: None` なら途中結果なしの今までの流れになる（`fetch_check` の比較と `compat_check` で使う）。
- **鍵の順番は「QueryStore → holder」に固定（BR1.2）**
  - `settle_inflight` は、store の鍵 1 回の中で、取り出し・確定・登録外しを行う。
  - 取得の流れは holder の鍵しか取らない。
  - 2 回数えないこと・落とさないことは、スレッドを使ったテストで確かめた。
- **viewVersion（BR1.4）**
  - view を作るとき、`settle_*`・`add_cached`・`begin_run`・`discard_all` のたびに進む。
  - 途中の評価だけが `ViewStamp` で照合する。最終の評価は、取得が終わったあとで保持が変わらないため、今の epoch だけの照合のまま。
- **途中の view の写し（Step 22）**
  - 1 回の鍵でまとめて写すと、30 万件で 58 ms・50 万件で 78 ms かかり、目安の 50 ms を超えた。
  - そこで 5 万件ずつ鍵を取り直して写すようにした（`INFLIGHT_COPY_CHUNK`。同じ時刻は塊の境目で分けない）。1 回の鍵は 8〜13 ms。
- **中断（BR3.1〜BR3.3）**
  - `after_fetch` が、取得の結果とセッションの答え（`FetchEnd`：Evaluate / EvaluateCancelled / Skip）から、次に何をするかを決める。
  - 中断後の評価は、abandon と画面を閉じる合図だけで止まる。
  - `StopHandle` には、`StopReason` を変えずに、共有の `AtomicBool` で abandon を足した。
- **rowKey（BR4.2）**：集計の行の鍵の列の数は `QueryResult::with_key_count` で持たせ、runner が plan から設定する。

## 残したこと

- **NFR1 の合否の数値はまだ決めていない。** 開発者の手元で、実際の AWS に対して `fetch_check --query … --partial-results on|off` を 3 回ずつ流し、その実測から決める（決めたら下げない）。
- **途中の view を作る間の store の鍵が長い。** 60 万件で約 143 ms、100 万件で約 600 ms かかる（並べ替えを含む）。その間に止まるのは、範囲の終わりの確定と評価の段だけで、取得のページは止まらない。
- **途中から最終への差し替えで、開いた行がまれに閉じる。** 写しの塊のあとに、それより前の時刻のページが届くと、イベントの順番の番号（seq）が途中と最終で食い違うことがあるため。件数と並びは保たれる。
- **書き出しの通知の添え書きは画面側で決めている。** 通知を閉じる前に次の実行が始まると、添え書きが消える。
- 手元の macOS と Windows での画面の確認は、まだしていない。
